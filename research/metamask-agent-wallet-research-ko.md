- **권한 내 거래도 사용자 의도를 위반할 수 있다.** 개별 거래가 권한 조건을 충족하더라도, 반복 실행으로 사용자가 유지하려던 자산 상태를 훼손하는 Authorization–Intent Gap이 발생할 수 있다.

## 1. 서론 및 배경 (Introduction)

### 1.1 AI Agent Wallet이 별도의 보안 모델을 필요로 하는 이유

일반적인 암호화폐 지갑에서는 사용자가 직접 거래 내용을 확인하고 서명한다. 반면, AI Agent Wallet에서는 AI 에이전트가 웹페이지, API 응답, 토큰 정보 등 외부 데이터를 바탕으로 사용자를 대신해 거래를 제안하거나 실행할 수 있다. 이 과정에서 에이전트는 신뢰할 수 없는 외부 입력에 지속적으로 노출되며, 프롬프트 인젝션이나 잘못된 추론, 과도한 권한 설정 등이 실제 금융 거래로 이어질 가능성이 존재한다.

이러한 환경에서는 AI 에이전트 자체를 신뢰 가능한 보안 경계로 두기 어렵다. AI 모델의 판단이나 시스템 프롬프트만으로 금융 행동을 통제하는 것이 아니라, 모델 외부의 별도 정책과 서명 계층을 통해 실제 권한을 제한할 필요가 있다.

이러한 위험은 특정 서비스에 한정된 문제가 아니라, AI가 금융 실행 권한을 갖는 구조 전반에서 발생할 수 있다. 실제 AI 에이전트 사례에서도 AI의 판단과 실제 금융 행동이 사용자의 의도와 다르게 나타난 경우가 확인되고 있다.

### 1.2 AI 에이전트의 판단과 사용자 의도 불일치 사례

AI Agent Wallet에서는 에이전트가 사용자를 대신해 거래를 생성하거나 실행할 수 있기 때문에, AI의 잘못된 판단이 실제 금융 행동으로 이어질 가능성이 존재한다.

특히 중요한 점은 이러한 문제가 반드시 개인 키 탈취나 스마트 컨트랙트 취약점의 형태로만 나타나는 것은 아니라는 것이다. AI가 외부 입력을 잘못된 명령으로 해석하거나 현재 자산 상태를 잘못 인식하더라도, 해당 거래가 지갑에 설정된 권한과 보안 정책을 위반하지 않는다면 실제 실행 단계까지 이어질 수 있다.

#### 1.2.1 Grok–BankrBot: 에이전트 간 신뢰 체인 악용

2026년 5월 Base 네트워크에서 Grok과 자동 거래 에이전트 BankrBot의 연결 구조를 악용한 [사건](https://slowmist.medium.com/behind-the-grok-exploitation-an-analysis-of-ai-agent-permission-chain-abuse-4d832d1bfc73)이 발생했다. 공격자는 사전에 Grok과 연결된 지갑의 Bankr Club Membership을 활성화해 BankrBot의 고권한 기능을 사용할 수 있는 상태를 만든 뒤, Grok에게 모스부호 형태의 메시지를 해독하도록 요청했다.

Grok은 해당 메시지를 평문으로 변환했고, 그 결과에는 BankrBot이 수행할 수 있는 자산 전송 명령이 포함되어 있었다. BankrBot은 Grok의 공개 응답을 실행 가능한 명령으로 인식해 실제 Base 네트워크에서 토큰 전송을 수행했다. SlowMist의 분석에 따르면 사건 이후 약 80~88%의 자금은 협상을 통해 반환됐다.

이 사건의 핵심은 Grok이 모스부호를 해독했다는 사실 자체가 아니다. 한 AI가 생성한 자연어 출력이 별도의 사용자 의도 확인 없이 다른 에이전트의 금융 권한과 연결됐다는 점이 문제였다. SlowMist 역시 이를 AI Agent 간 permission chain이 악용된 사례로 분석했다.

따라서 거래가 기존 권한 범위 안에서 정상적으로 실행될 수 있다는 사실만으로는, 해당 거래가 실제 사용자가 의도한 금융 행동인지까지 보장하기 어렵다는 점을 보여준다.

#### 1.2.2 Lobstar Wilde: 에이전트의 상태 인식 실패

2026년 2월 Solana에서 AI 에이전트 Lobstar Wilde가 약 4 SOL 상당의 자산을 전송하려다 지갑에 보유하고 있던 약 5,200만 개의 LOBSTAR 토큰 전체를 전송하는 [사건](https://pashpashpash.substack.com/p/my-lobster-lost-450000-this-weekend)이 발생했다. 이는 전체 토큰 공급량의 약 5%에 해당했다.

개발자 Nik Pash의 사후 분석에 따르면 사건 이전 도구 오류로 기존 세션이 비정상 종료된 뒤 새로운 세션이 시작됐다. 파일에 저장돼 있던 에이전트의 성격과 도구 정보는 복구됐지만, 기존 대화에만 존재하던 지갑의 자산 상태에 대한 인식은 복구되지 않았다.

이후 Lobstar Wilde는 약 4 SOL 상당의 LOBSTAR 토큰을 추가로 구매한 뒤 지갑 잔액을 확인했다. 하지만 기존 보유량을 인지하지 못한 상태에서 전체 잔액을 방금 구매한 물량으로 잘못 해석했고, 결국 약 5,200만 개의 토큰 전체를 전송했다.

블록체인 관점에서 해당 거래 자체는 정상적으로 처리됐다. 그러나 사용자가 기대한 것은 약 4 SOL 상당의 자산 이전이었고, 실제 결과는 지갑의 LOBSTAR 보유량 전체가 이전되는 것이었다. 즉 거래의 기술적 유효성과 실제 실행 결과가 사용자의 거래 의도와 일치하는지는 별개의 문제라는 점을 보여준다.

#### 1.2.3 두 사례가 보여주는 공통적인 문제

Grok–BankrBot과 Lobstar Wilde는 발생 원인은 서로 다르다.

Grok–BankrBot은 외부 입력이 AI를 거쳐 금융 명령으로 연결되는 권한 및 신뢰 경계의 문제에 가깝고, Lobstar Wilde는 세션 초기화와 지갑 상태 인식 상실 이후 에이전트가 예상과 크게 다른 행동을 실행한 자율 실행 오류 사례에 가깝다.

그러나 두 사건에는 공통점이 존재한다.

> **AI의 판단이 실제 거래로 이어지는 과정에서는, 해당 거래가 사용자의 거래 의도와 일치하는지를 독립적으로 확인하는 기준이 중요하다.**

AI가 사용자의 의도와 다른 거래를 생성하더라도, 해당 거래가 기존에 설정된 권한과 보안 정책의 범위 안에 있다면 실행 단계까지 이어질 수 있다.

이러한 사례들은 AI Agent Wallet에서 에이전트에게 부여되는 권한과 실제 거래 실행 범위를 보다 세밀하게 통제할 필요성을 보여준다. 이를 위해 Allowlist, 지출 한도, 거래 시뮬레이션과 같은 보호 장치가 활용된다.

### 1.3 MetaMask Agent Wallet의 현재 보안 구조

이러한 접근의 사례로 MetaMask Agent Wallet을 들 수 있다. MetaMask Agent Wallet은 AI 에이전트를 신뢰 가능한 주체로 간주하기보다 거래를 제안하거나 제한된 범위에서 실행하는 주체로 취급하고, 모델 외부의 보안 정책을 통해 실제 실행 권한을 통제한다.

MetaMask Agent Wallet의 기본적인 [보안 전략](https://metamask.io/ko/news/agentic-wallet-security)은 AI 에이전트와 실제 서명 환경을 분리하고, 외부 보안 정책을 통해 에이전트가 수행할 수 있는 행동의 범위를 제한하는 것이다.

이를 위해 MetaMask는 에이전트와 실제 서명 환경을 분리하고, 키를 에이전트가 직접 접근할 수 없는 TEE 기반 환경에서 관리한다. 또한 지원되는 EVM 거래에는 거래 시뮬레이션, Threat Scan, MEV Protection으로 구성된 보안 파이프라인을 적용한다.

운영 모드에 따라 추가적인 권한 제한도 적용된다. Guard Mode에서는 네트워크·주소·토큰 수신자 Allowlist와 24시간 출금 한도를 통해 에이전트의 실행 범위를 제한하며, 정책 범위를 벗어나거나 위험이 탐지된 거래에는 2FA를 통한 사용자 승인을 요구한다. Beast Mode에서는 이러한 Allowlist와 출금 한도가 적용되지 않지만, 거래에 대한 보안 검사는 계속 수행된다.

이러한 보호 기능은 크게 세 가지 역할로 볼 수 있다.

첫째, 키 격리를 통해 AI 에이전트가 개인 키에 직접 접근하는 위험을 줄인다.

둘째, Guard Mode의 Allowlist와 출금 한도 등을 통해 에이전트가 수행할 수 있는 거래의 범위를 사전에 제한한다.

셋째, Threat Scan과 Simulation을 통해 실제 거래가 전송되기 전에 위험을 검사하고, 정책을 벗어나거나 위험이 탐지된 거래에는 2FA를 통한 사용자 확인을 추가한다.

즉, 현재 MetaMask Agent Wallet의 보안 구조는 AI 모델을 신뢰하는 방식보다는 AI 외부에 별도의 정책 계층을 두고 금융 권한 자체를 제한하는 구조라고 볼 수 있다.

## 2. 문제 정의 (Problem Statement)

### 2.1 기존 정적 검사의 사각지대

#### 2.1.1 MetaMask Smart Accounts Kit와 Caveat Enforcer의 조건부 검증 메커니즘

MetaMask Smart Accounts Kit는 MetaMask Agent Wallet 구축 및 제어를 지원하는 공식 툴킷이다. 해당 툴킷은 권한 위임(Delegation) 구조를 활용하여 권한 설정과 기능 공유를 지원한다.
[MetaMask Delegation Toolkit](https://metamask.io/ko/news/introducing-the-delegation-toolkit-metamask-smart-contract-account-offering)은 현재 Arbitrum, Avalanche, Base, Linea, Optimism, Polygon을 포함해 User Operation Bundler가 지원하는 모든 EVM 체인에서 호환된다. Smart Accounts Kit는 위임에 대한 규칙과 제한 사항을 강제하는 스마트 컨트랙트인 Caveat Enforcer를 제공하며, 이는 Delegation Framework 내에서 조건부 트랜잭션 실행을 통제하는 핵심 메커니즘이다. 즉, Caveat Enforcer는 특정 트랜잭션에 위임 권한이 유효한지 검증하고, 정의된 기준의 충족 여부를 평가하는 역할을 수행한다.

#### 2.1.2 정적 속성 검사의 보호 범위와 예상 사후 상태 검증의 필요성

현재 Caveat Enforcer는 호출 대상 주소, 함수, 전송 금액 등 개별 트랜잭션 단위의 권한 조건을 검증하는 데 초점이 맞춰져 있다. `afterHook`을 통해 실행 직후 단일 자산의 잔액 차분을 확인하는 기능이 지원되나, 이는 주로 개별 트랜잭션 단위의 무결성 검사에 해당한다. [공식 툴킷 문서](https://docs.metamask.io/smart-accounts-kit/concepts/delegation/caveat-enforcers) 역시 Caveat Enforcer가 "실행 과정을 보호하지만 상환 이후의 사후 상태(final state post-redemption)를 보장하지는 않는다"고 명시하며, 결합된 Caveat Enforcer들이 미치는 전체적인 영향을 고려할 것을 권장한다.

이러한 단일 트랜잭션 기반의 권한 조건 통제 구조에서는 권한이 정상적으로 승인되더라도 예상 사후 상태가 훼손되는 사각지대가 발생한다. 시작 잔액이 10,000 토큰일 때, 트랜잭션당 최대 500 토큰 전송을 허용하는 권한 조건과 트랜잭션 후 최소 9,700 토큰을 유지해야 하는 사용자 승인 결과 정책이 결합된 환경을 가정한다. 에이전트가 500 토큰 전송 트랜잭션 후보를 생성할 경우, 해당 후보는 지출 한도 권한 조건을 충족하여 기존 Caveat Enforcer의 온체인 검증을 통과한다. 그러나 실행 시 예상 사후 상태는 9,500 토큰이므로, 설정된 사용자 승인 결과 정책을 위반하게 된다.

따라서 결과 상태 검증 계층(Result State Verification Layer)은 기존 Caveat Enforcer의 세분화된 접근 제어(Granular Access Control) 구조를 대체하지 않는다. 기존 권한 검증 메커니즘을 유지한 상태에서, 사용자 승인 결과 정책을 트랜잭션 브로드캐스트 직전에 추가로 평가하는 보완적 계층(Complementary Layer)으로 동작한다.

개별 트랜잭션의 권한 조건을 준수하더라도 다수의 프로토콜을 거치며 누적되는 슬리피지나 반복 실행으로 인한 전체 포트폴리오 가치 하락 등 복합적인 예상 사후 상태를 통제하기 위해서는, 기존 권한 위임 구조 위에 독립된 추가 보호 계층이 요구된다.

#### 2.1.3 ERC-4337 사전 시뮬레이션과 사용자 승인 결과 정책 평가의 구분

스마트 계정의 검증 가능 여부는 서명이나 호출 데이터와 같은 입력값뿐만 아니라 논스, 예치금, 계정·Factory·Paymaster의 코드와 상태 등 가변적인 체인 상태에도 의존한다. [ERC-4337](https://eips.ethereum.org/EIPS/eip-4337#useroperation-simulation)은 이러한 특성에 따라 Bundler가 `UserOperation`을 멤풀에 수용하기 전에 오프체인 시뮬레이션을 통해 검증 단계의 유효성을 확인하도록 한다.

그러나 [ERC-4337이 규정하는 시뮬레이션](https://eips.ethereum.org/EIPS/eip-4337#simulation-specification)은 주로 검증 단계에서 수행되는 `validateUserOp`과 `validatePaymasterUserOp` 등이 현재 체인 상태에서 정상적으로 통과하는지를 확인하기 위한 절차이며, `UserOperation`의 실행으로 발생하는 전체 사후 상태를 검증하는 절차는 아니다. 별도의 실행 시뮬레이션을 통해 예상 사후 상태를 계산하더라도, 이를 사용자가 사전에 승인한 지갑 수준의 결과 정책과 대조하고 실행 허용 또는 중단으로 연결하는 절차는 결과 상태 검증 계층에서 별도로 설계되어야 한다.

기존의 권한·Caveat 기반 Agent Wallet 보호 메커니즘은 호출 대상, 함수, 금액 한도 등 사전에 표현된 실행 제약을 통해 권한 오남용을 제한한다. 그러나 이러한 조건을 통과한 거래 후보라도 예상 사후 상태가 사용자 승인 결과 정책을 위반할 수 있으므로, 이를 실행 직전에 판정하고 거래를 중단할 수 있는 보완 계층이 필요하다.

## 3. 제안 및 타당성 (Methodology)

#### 3.1.1 사용자 승인 결과 정책 기반 보호 계층

결과 상태 검증 계층은 기존 Agent Wallet의 권한 기반 보호를 대체하지 않고 그 이후 단계에 결합된다. 에이전트가 생성한 거래가 Allowlist, 호출 조건, 거래당 한도 등 기존 Caveat의 권한 조건을 충족하더라도, 예상되는 거래 후 지갑 상태가 사용자 승인 결과 정책을 위반하면 실행을 중단한다.

사용자 승인 결과 정책은 보호할 사후 상태를 명시적으로 표현한 조건이다. 예를 들어 “이 지갑에서 USDC를 최소 0.5개 남겨줘”라는 요청은 특정 자산의 거래 후 잔액이 0.5 USDC 이상이어야 한다는 잔액 하한 정책으로 표현될 수 있다. 에이전트가 거래 후보를 생성하면 결과 상태 검증 계층은 현재 체인 상태에서 해당 거래를 사전 시뮬레이션하여 예상 사후 상태를 계산한다. 결정론적 평가기는 예상 잔액이 승인된 하한 이상인지 확인한다. 예상 잔액이 0.9 USDC이면 정책을 충족하고, 0.4 USDC이면 기존 전송 한도 이내의 거래라도 실행 요청을 중단한다.

시작 잔액이 10,000 토큰이고 기존 Caveat가 거래당 최대 500 토큰의 전송을 허용한다고 가정한다. 거래 후 최소 9,700 토큰을 유지해야 한다는 사용자 승인 결과 정책을 함께 적용할 수 있다. 500 토큰 전송은 기존 Caveat의 금액 제한을 충족하지만, 예상 사후 잔액은 9,500 토큰이므로 사용자 승인 결과 정책을 위반한다. 이 경우 기존 권한 검사가 실패한 것은 아니다. 권한 조건이 표현하지 않는 결과 조건을 결과 상태 검증 계층이 추가로 집행한다.

정책의 의미를 해석하는 단계와 최종 거래를 판정하는 단계는 분리된다. 사용자는 대상 자산, 비교 조건과 임계값이 포함된 정책을 검토하고 승인한다. 실행 단계에서는 승인된 정책과 시뮬레이션 결과만을 입력으로 사용하는 결정론적 평가기가 허용 여부를 판정한다. 에이전트는 실행 시점에 사용자의 의도를 재해석하거나 안전성을 자율적으로 판단하지 않고, 승인된 정책을 예상 사후 상태에 적용한다.

결과 상태 검증 계층은 ERC-4337이 제시하는 상태 의존적 사전 검증 원리와 연결된다. [ERC-4337](https://eips.ethereum.org/EIPS/eip-4337#useroperation-simulation)은 스마트 계정의 검증이 가변적인 EVM 상태에 의존할 수 있으므로, `UserOperation`을 멤풀에 수용하거나 번들에 포함하기 전에 검증 단계를 시뮬레이션하는 절차를 제시한다. 결과 상태 검증 계층은 이러한 사전 검증 원리를 실행 단계까지 확장하여 거래 후보를 별도로 실행 시뮬레이션하고, 계산된 예상 사후 상태를 사용자 승인 결과 정책의 평가 입력으로 활용한다. 시뮬레이션 시점과 실제 실행 시점 사이에는 상태가 변경될 수 있으므로, 검증한 거래 후보와 실제 실행 요청의 동일성 및 관련 상태의 유효성을 실행 경계에 가까운 시점에 다시 확인해야 한다.

#### 3.1.2 Intent 기반 결과 조건 검증과의 관계

블록체인 분야에서는 사용자가 구체적인 실행 경로 대신 원하는 결과와 허용 조건을 제시하는 Intent 기반 거래가 발전해 왔다. 사용자는 예를 들어 “1 ETH를 사용하되 최소 3,000 USDC를 수령한다”와 같은 조건에 서명하고, Solver 또는 Filler가 해당 조건을 만족하는 실행 경로를 탐색하도록 할 수 있다. Intent가 반드시 자연어를 의미하는 것은 아니다. 기존 프로토콜에서 Intent는 토큰 종류, 수량, 가격, 유효 기간 등을 포함하는 구조화된 주문으로 표현되는 경우가 일반적이다. 핵심은 실행 경로의 선택을 외부 주체에 맡기면서도 사용자가 승인한 결과 조건을 유지하는 데 있다.

주문형 Intent 프로토콜의 대표 사례인 CoW Protocol과 UniswapX는 특정 교환 주문의 결과 조건을 보호한다. [CoW Protocol](https://docs.cow.fi/cow-protocol/reference/core/intents)에서 사용자는 판매·구매 자산, 수량, 가격 조건, 유효 기간 등을 포함한 주문에 서명하고, Solver는 이를 만족하는 정산안을 구성한다. 정산 과정에서는 주문의 제한 조건이 충족되어야 하며, Solver는 사용자가 허용한 범위를 벗어난 결과를 임의로 실행할 수 없다. [UniswapX](https://developers.uniswap.org/docs/liquidity/uniswapx/overview) 역시 사용자가 입출력 토큰과 수량, 가격 변화 규칙, 유효 기간 등을 포함한 주문에 서명하고, Filler가 이를 이행하는 구조를 사용한다. Reactor는 주문을 정산하며, Dutch Order에서는 시간에 따라 변하는 가격 조건도 사용자가 사전에 승인한 규칙의 범위 내에서 적용된다.

이들 프로토콜은 실행 경로를 탐색하는 주체와 결과 조건을 검증하는 주체를 분리한다. 외부 Solver 또는 Filler는 유동성 경로를 탐색할 수 있지만, Settlement 또는 Reactor의 검증을 통과하지 못하면 주문을 이행할 수 없다. 보호 범위는 기본적으로 해당 주문의 교환 결과이다. 개별 스왑이 최소 수령량과 최대 지출량을 충족하더라도, 거래 후 지갑에 특정 자산을 최소 얼마만큼 유지해야 하는지 또는 여러 거래에 걸친 누적 손실을 어디까지 허용하는지는 주문에 별도 조건으로 표현하지 않는 한 자동으로 집행되지 않는다.

보다 일반적인 Intent 구조는 상태 변화와 검증 가능한 조건을 넓은 범위에서 표현하려는 흐름을 보인다. [ERC-7521](https://eips.ethereum.org/EIPS/eip-7521)은 스마트 컨트랙트 지갑이 다양한 Intent Standard를 수용할 수 있도록 제안된 일반화된 Intent 명세 초안이다. 사용자가 서명한 `UserIntent`는 Solver에 의해 다른 Intent와 결합되어 `IntentSolution`으로 구성될 수 있으며, 개별 Intent의 구체적인 의미와 검증 방식은 사용자가 선택한 Intent Standard에서 정의한다. 따라서 ERC-7521은 결과 조건 자체를 하나의 형식으로 정의하기보다 다양한 Intent 형식과 검증 로직을 수용하기 위한 공통 실행 구조에 가깝다.

[Anoma](https://anoma.net/blog/an-introduction-to-intents-and-intent-centric-architectures) 역시 Intent를 사용자의 선호와 제약을 반영한 상태 전이 조건으로 설명한다. Solver는 Intent를 만족하는 거래를 구성하고, Validity Predicate는 계산된 상태 전이가 허용되는지 검증한다. 상태 전이를 생성하는 주체와 해당 상태 전이가 규칙을 만족하는지 판정하는 주체를 분리한다는 점에서 결과 상태 검증 계층과 논리적 접점을 가진다. [OMNIINTENT](https://arxiv.org/abs/2603.04168) 또한 Intent를 검증 가능한 제약 언어로 표현하고 runtime constraint와 실행 가능성 예측을 결합하려는 연구 흐름으로 볼 수 있다. 다만 해당 연구는 사전 공개 논문 단계이므로, 확립된 표준이나 상용 프로토콜과 같은 수준의 구현 보장으로 해석하지 않는다.

결과 조건 검증 자체는 기존 기술에도 존재한다. CoW Protocol과 UniswapX는 주문 수준의 결과 조건을 다루며, ERC-7521은 다양한 Intent Standard를 수용하는 공통 구조를 제시하고, Anoma는 보다 일반적인 상태 전이 조건을 제시한다. 결과 상태 검증 계층은 기존 Agent Wallet의 위임·권한 보호를 통과한 거래 후보에 사용자 승인 결과 정책을 실행 직전에 명시적으로 적용하는 구조에 해당한다.

#### 3.1.3 보호 범위와 설계 요구사항

결과 상태 검증 계층은 기존 Caveat, 최소 수령량 검사 또는 온체인 정산 조건을 대체하지 않는다. [Caveat](https://docs.metamask.io/smart-accounts-kit/concepts/delegation/caveat-enforcers/)는 위임 권한과 개별 실행 조건을 제한하고, [주문형 Intent 프로토콜](https://docs.cow.fi/cow-protocol/reference/core/intents)은 특정 주문의 교환 결과를 보호하며, 결과 상태 검증 계층은 지갑 수준의 정책을 추가로 집행한다. 세 가지 보호 방식은 서로 다른 대상과 위치에서 동작하는 보완 관계이다.

보호 대상은 사용자가 검토하고 승인한 정책에 명시된 결과 조건이다. 자산별 최소 잔액, 누적 지출 한도 또는 정의된 방식에 따른 포트폴리오 가치 하한 등이 이에 해당할 수 있다. 사용자가 승인하지 않은 숨은 의도나 수령 자산의 가격 변동까지 고려한 경제적 손실은 자동으로 판단하지 않는다. 포트폴리오 가치나 누적 지출을 검사하려면 가격 정보의 출처, 평가 시점, 자산 범위뿐만 아니라 누적 기간, 집계 대상과 이력의 저장·조회 기준을 정책에 별도로 포함해야 한다.

결과 상태 검증 계층은 다음 요구사항을 충족해야 한다.

1. 기존 권한 보호를 대체하지 않고 기존 Caveat 검사를 통과한 이후 실제 실행 요청이 전송되기 전에 결합되어야 하며, 보호 대상 거래가 해당 계층을 우회하지 않도록 해야 한다.

2. 거래의 호출 대상이나 금액과 같은 입력값뿐만 아니라 실행 시뮬레이션으로 계산한 예상 사후 상태를 검사해야 한다.

3. 판정 기준은 에이전트의 자율적 판단이 아니라 사용자가 검토하고 승인한 사용자 승인 결과 정책이어야 한다.

4. 자연어 또는 사용자 요청의 해석 단계와 최종 거래의 허용·거절 판정 단계를 분리해야 한다.

5. 검사한 거래 후보와 실제 실행 요청이 동일한지 확인해야 한다. [이를 위해 네트워크, 계정, 대상, 호출 데이터와 금액뿐만 아니라](https://eips.ethereum.org/EIPS/eip-4337#the-useroperation-structure) [nonce](https://eips.ethereum.org/EIPS/eip-4337#the-useroperation-structure)[, 가스·수수료, Paymaster 정보 등 실행 결과에 영향을 줄 수 있는 필드를 함께 검증해야 한다.](https://eips.ethereum.org/EIPS/eip-4337#the-useroperation-structure)

6. 검증 이후 상태가 변경될 가능성을 줄이기 위해 상태 확인과 정책 집행을 가능한 한 실행 경계에 가까운 위치에서 수행해야 한다. 다만 오프체인 시뮬레이션과 실제 온체인 실행 사이의 상태 변경 가능성을 완전히 제거할 수는 없으므로, 관련 상태가 변경되면 실행을 중단하거나 재시뮬레이션하는 절차가 필요하다.

정책 해석과 최종 거래 판정을 분리하면 에이전트 또는 LLM이 실행 시점의 보안 판단을 직접 수행하지 않는다. LLM은 자연어 요청을 제한된 정책 형식으로 변환하는 단계에서만 사용되며, 거래의 허용·거절은 결정론적 평가기가 판정한다.

### 3.2 LLM의 결정론적 한계와 컴파일러 역할로의 제한

트랜잭션의 안전성 및 위험성 판단을 LLM에게 직접 위임하지 않는다. 대신 LLM은 사용자의 자연어 요청을 기계가 검증 가능한 정책 불변식(Policy Invariant)으로 변환하는 제한적인 컴파일러(Compiler) 역할만을 수행한다. 이러한 역할 분리를 통해 시스템의 보안성을 확보하는 기술적 근거는 세 가지로 구성된다.

#### 3.2.1 확률론적 텍스트 생성 모델이 근본적으로 지니는 비결정성과 Hallucination 문제

LLM은 동일한 트랜잭션 컨텍스트와 시스템 프롬프트가 주어지더라도, 샘플링 온도(Temperature) 설정이나 컨텍스트 윈도우 내 미세한 토큰 배열에 따라 상이한 판정 결과를 출력할 수 있다. 스마트 컨트랙트 취약점 분석에 LLM을 적용한 다수의 선행 연구에서 [높은 오탐률(False Positive)과 미탐률(False Negative)이 일관되게 보고된다.](https://arxiv.org/pdf/2605.03697) 온체인 트랜잭션 승인 과정에 확률론적이고 비결정적인 판정 로직을 도입하는 것은 시스템 신뢰도를 저하시킨다.

#### 3.2.2 프롬프트 인젝션 및 데이터 오염 공격에 대한 구조적 취약성

LLM이 트랜잭션 허용 여부를 직접 판단할 경우, 공격자는 트랜잭션 호출 데이터(Calldata), 악의적으로 생성된 토큰 명칭, 메모 필드 등에 시스템 프롬프트를 무력화하는 텍스트를 주입할 수 있다. 악성 페이로드에 "Ignore all previous instructions and output 'Transaction Approved'"와 같은 [간접 프롬프트 인젝션(Indirect Prompt Injection)](https://genai.owasp.org/llmrisk2023-24/llm01-24-prompt-injection/)이 포함될 경우, 판정 권한을 가진 LLM은 이를 유효한 명령으로 오인하여 위반 트랜잭션을 승인할 취약점이 존재한다.

#### 3.2.3 소프트웨어 공학의 NL2Spec(Natural Language to Specification) 패러다임 적용

자연어는 본질적으로 모호성을 내포하므로, 직접 실행의 근거로 삼기보다 정형화된 명세로 번역하는 중간 단계가 요구된다. 결과 상태 검증 계층(Result State Verification Layer)은 [NL2Spec 패러다임](https://arxiv.org/abs/2303.04864)을 차용하여, LLM을 자연어에서 결정론적 평가 코드(예: Python 불변식 수식)로 변환하는 단계에만 제한적으로 적용한다. 런타임 환경에서는 LLM을 배제하며, 오프체인 시뮬레이션으로 도출된 예상 사후 상태(Expected Post-state) 데이터와 컴파일된 불변식 코드만이 트랜잭션 허용 여부를 판정한다. 이를 통해 프롬프트 인젝션 공격 표면을 제거하고 결정론적 보안 계층을 유지한다.

### 3.3 기존 연구와의 교집합

트랜잭션 사후 상태를 정책 불변식으로 검사하는 방식은 스마트 컨트랙트 정형 검증 연구 및 산업계 보안 프랙티스에서 입증된 상태 기반 검증(State-based Verification) 모델과 논리적 접점을 공유한다.

#### 3.3.1 Solythesis, 런타임 불변식 검증을 통한 상태 기반 보안

스마트 컨트랙트의 런타임 불변식 검증 구조는 꾸준히 연구되어 왔다. [USENIX Security 2020에 발표된 "Solythesis" 논문](https://www.cs.toronto.edu/~fanl/papers/solythesis-pldi20.pdf)은 소스코드 수준에 개발자 정의 불변식을 계측(Instrumentation)하여, 런타임 중 취약점 공격이나 비정상 상태 전이로 불변식이 위반될 경우 해당 트랜잭션을 롤백하는 구조를 제안했다. 이는 트랜잭션의 표면적 실행 경로와 무관하게 사후 상태의 정책 부합 여부를 검사하는 방식이 런타임 보안 검증에 효과적임을 실증한 사례다.

#### 3.3.2 Safe Transaction Guards의 사후 상태 대조 메커니즘

이더리움(Ethereum) 생태계의 스마트 계정 인프라인 [Safe의 Transaction Guards](https://docs.safe.global/advanced/smart-account-guards)는 트랜잭션 실행 전뿐만 아니라 실행 완료 직후 지갑 상태 변화를 대조하는 훅(Hook) 구조를 제공한다. 스마트 계정이 수행한 작업이 사후에 조건 범위를 벗어난 자산 유출을 일으킬 경우, 온체인 상에서 해당 트랜잭션을 즉시 롤백하는 메커니즘을 지원한다.

#### 3.3.3 오프체인 시뮬레이션과 LLM 컴파일러의 융합

기존 상태 검증 방식은 구조적 제약이 따른다. Solythesis 방식은 기배포된 외부 디파이(DeFi) 프로토콜에 범용적으로 계측 코드를 적용하기 어려우며, Safe Transaction Guards와 같이 온체인 스마트 컨트랙트 내부에서 다중 자산 계산이나 포트폴리오 가치 산정을 수행할 경우 연산에 따른 가스비(Gas Fee) 소모가 크게 증가한다.
결과 상태 검증 계층은 이러한 한계를 보완하기 위해 다음과 같은 구조를 결합한다.

- **오프체인 시뮬레이션 기반 검증:** 온체인이 아닌 트랜잭션 브로드캐스트 직전 오프체인 시뮬레이터(Anvil, Tenderly 등) 환경에서 예상 사후 상태를 사전 연산하고 불변식을 평가하여 온체인 연산 비용 제약을 해소한다.

- **LLM 컴파일러 결합:** 사용자의 자연어 요청을 LLM 기반 컴파일러를 통해 정형화된 정책 불변식으로 번역함으로써, 하드코딩된 복잡한 스키마 없이 사용자 승인 결과 정책을 시스템에 통합한다.

이러한 결합 구조는 상태 기반 검증의 보안성을 유지하면서, 오프체인 실행을 통해 연산 비용 문제를 완화하고 LLM 컴파일러를 통해 정책 접근성을 개선한다.

## 4. 아키텍처 (Architecture)

### 4.1 결과 상태 검증의 구성과 실행 경로

결과 상태 검증 계층은 승인된 정책을 기준으로 후보 거래의 예상 사후 상태를 평가하고, 그 판정에 따라 실행 요청을 허용하거나 중단한다. 이때 실행 여부를 통제하는 부분을 결과 게이트라 한다. 정책을 충족한 후보를 실행 단계로 전달하려면, 승인된 정책과 검증 대상 거래가 변경되지 않았으며 판정에 사용한 상태가 여전히 유효한지도 확인해야 한다.

#### 4.1.1 정책의 표현과 승인 기록

정책은 대상 자산과 유지해야 할 조건을 정해진 형식으로 표현한다. 예를 들어 “USDC를 최소 0.5개 남겨줘”라는 요청은 대상 자산을 USDC로, 거래 후 최소 잔액을 0.5개로 지정한 잔액 하한 정책(`assetBalanceFloor`)에 해당한다.

LLM이 제안한 정책은 승인 단계를 거친 뒤 검증 기준으로 사용된다. 정책의 해시를 승인 기록과 후보 거래에 함께 기록하여, 후보가 참조하는 정책이 승인 기록에 연결된 정책과 동일한지 확인한다. 이 해시는 정책 내용의 일치성과 변경 여부를 확인하기 위한 값이며, 승인 주체의 신원이나 승인 행위 자체를 증명하지는 않는다.

승인 이후의 정책 판정에는 LLM의 추가 판단을 사용하지 않는다. 결정론적 평가기는 후보의 예상 사후 잔액이 승인된 하한 이상인지 비교한다. 예상 잔액이 하한과 같으면 조건을 충족하며, 하한보다 작으면 위반으로 판정한다. 예를 들어 하한이 0.5 USDC일 때 예상 잔액 0.9 USDC는 이 조건을 충족하지만, 0.4 USDC는 충족하지 않는다. 결과 게이트는 이러한 정책 판정과 거래·상태의 일치 여부를 함께 확인하여 실행 단계로 전달할 후보를 결정한다.

#### 4.1.2 검증 대상과 실행 요청의 연결

예상 사후 상태가 정책을 충족하더라도 실제로 실행되는 거래가 검증한 거래와 다르면 해당 판정을 적용할 수 없다. 따라서 검증한 거래와 실제 실행 요청이 같은 네트워크·계정을 사용하며, 전송 대상·금액·실행할 기능도 같은지 대조한다. 각 거래 후보에는 검사 기준으로 사용한 정책과 승인 기록도 연결하여, 실행 요청이 승인된 조건에 따라 검증한 거래인지 확인한다. 이는 소액 전송을 검증한 뒤 실제 요청을 더 큰 금액으로 바꾸는 등의 거래 치환을 방지하기 위한 검사다.

거래 내용이 같더라도 실행의 시작 상태가 달라지면 예상 결과가 달라질 수 있다. 이에 따라 잔액과 거래 순번인 논스(`nonce`) 등 판정에 사용한 상태도 다시 확인한다. 거래 동일성 검사가 실행 대상의 변경 여부를 확인한다면, 상태 확인은 기존 허용 판정을 계속 사용할 수 있는지 판단하는 절차다. 확인 시점 이후에 발생하는 상태 변경의 영향은 실험 C에서 별도로 평가한다.

#### 4.1.3 기존 권한 제한과 결과 게이트의 결합

Delegation Framework의 Caveat는 위임된 거래에 적용되는 권한 제한 규칙이며, Caveat Enforcer가 해당 조건을 집행한다. 거래 대상과 호출 기능을 제한하고, 설정에 따라 잔액 감소량과 기간별 전송량도 검사한다.

결과 게이트는 이 기존 구성을 유지하면서 별도로 승인된 상태 조건을 적용한다. 예를 들어 한 번의 거래에서 최대 500 토큰의 감소를 허용하는 규칙과, 거래 후 최소 9,700 토큰을 유지해야 하는 정책은 같은 후보에 함께 적용될 수 있다. 시작 잔액이 10,000 토큰일 때 500 토큰 전송은 기존 감소 상한을 충족하지만, 예상 잔액 9,500 토큰은 추가된 하한을 충족하지 않는다.

실험 A에서는 여섯 Caveat와 서명된 위임을 유지하고, 전송 거래의 서명·전송 단계 앞에 결과 게이트를 추가했다. 게이트를 통과한 후보는 기존 위임 실행 절차로 전달되며, 실제 실행 과정에서도 Caveat가 적용된다. 결과 조건을 위반한 후보는 해당 전송 거래의 서명 전에 중단된다.

#### 4.1.4 지갑 연결과 검증 위치

결과 게이트가 판정에 사용하는 예상 사후 상태는 후보 거래를 실제로 전송하기 전에 오프체인에서 시뮬레이션하여 산출한다. 이 상태를 사용자 승인 결과 정책과 비교한 뒤 실행 요청의 허용 여부를 결정한다.

실제 Agent Wallet과 연결한 경로에서는 지갑에 거래 실행을 요청하기 전인 `pre-submit` 단계에 결과 게이트를 배치했다. 후보가 승인된 조건을 충족하면 잔액과 논스 등을 다시 확인한 뒤 지갑에 실행을 요청한다. 이후 지갑의 Guard Mode와 추가 인증 등 기존 실행 절차가 이어진다. 조건을 위반한 후보는 지갑 요청 전에 중단된다.

이 게이트는 Agent Wallet을 호출하는 애플리케이션에 배치되어 있다. 실험 B에서는 해당 경로를 사용한 Sepolia 직접 USDC 전송의 허용·거절 기록을 확인했다.

검증 위치의 영향을 살펴보기 위해 실험 C에서는 로컬에 `pre-submit` 경로와 서명 직전 상태를 확인하는 `pre-sign` 경로를 구성했다. `pre-sign` 경로는 런타임 상태가 사전 검증 시점의 컨텍스트와 일치하지 않으면 이를 `STALE_CAPTURED_CONTEXT`로 탐지하고, 기존 판정을 사용하지 않은 채 후보를 중단한다. 이는 실제 Agent Wallet 내부에 통합한 기능이 아니라 검증 위치를 비교하기 위한 통제 경로다.

#### 4.2.1 ERC-4337의 상태 의존적 사전 검증(`simulateValidation`)

상태에 의존하는 사전 검증의 사례로 ERC-4337의 검증 구조가 있다. 일반적인 EOA(Externally Owned Account) 트랜잭션은 서명 검증, 논스, 잔액, 가스 한도 등 EVM 상태와 무관한 정적 검사만으로도 유효성을 확정할 수 있다. 반면 스마트 컨트랙트 기반의 계정 추상화 환경에서는 `UserOperation`의 유효성이 `validateUserOp`나 `validatePaymasterUserOp`와 같은 검증 함수를 통해 가변적인 EVM 상태에 직접적으로 의존한다. 공식 ERC-4337 명세의 Simulation Rationale 섹션은 Bundler가 트랜잭션을 멤풀에 포함하기 전에 오프체인 샌드박스 환경에서 `simulateValidation`을 수행하여, 다른 작업과 격리된 상태에서 유효성을 사전 검증하도록 규정한다. 상태 기반의 실행 가능 여부를 시뮬레이션으로 사전에 확인하는 것은 계정 추상화 인프라의 공식적인 표준 절차다.

#### 4.2.2 ERC-7562의 검증 범위 규칙과 전송 직전 재검증

ERC-7562(Account Abstraction Validation Scope Rules)는 계정 추상화의 검증 단계에서 상태 의존성으로 인한 무효화와 서비스 거부(DoS) 위험을 제한하기 위한 규칙을 정의한다. 오프체인 시뮬레이션이 완료된 시점과 실제 온체인에 포함되는 시점 사이에 상태가 변경되면, 사전 검증을 통과한 `UserOperation`이 온체인 검증에서 실패할 수 있다. ERC-7562는 검증 구간에서 사용할 수 있는 Opcode와 스토리지 접근 범위를 제약하여 이러한 위험을 제한한다. 다만 이 규칙이 거래 실행 이후의 자산 상태와 시뮬레이션 결과의 일치까지 보장하는 것은 아니다. 제안된 파이프라인은 시뮬레이션 직후 결정론적 불변식을 평가하고, 브로드캐스트 직전 논스와 잔액 컨텍스트를 다시 확인하여 앞선 판정을 계속 사용할 수 있는지 검사한다.

#### 4.2.3 EVM 상태 포크와 상태 차분 추출 인프라

이러한 시뮬레이션을 지원하는 노드와 개발 인프라도 구축되어 있다. Geth(Go-Ethereum)의 `eth_call` 및 State Override 기능은 실제 체인 상태를 변경하지 않고 계정 잔액이나 스토리지를 임시로 덮어쓴 상태에서 EVM 호출을 실행할 수 있도록 지원한다. `eth_call`은 호출의 반환값을 제공하며, 실행 전후의 상태 차분은 `debug_traceCall`에서 `prestateTracer`의 `diffMode`를 사용하는 등의 추적 기능으로 추출할 수 있다. Foundry의 Anvil이나 Tenderly 역시 RPC를 통해 특정 블록 시점의 체인 상태를 포크하여, 해당 시점의 네트워크 상태를 기반으로 한 환경에서 트랜잭션 실행 전후의 상태 차분을 분석할 수 있도록 지원한다.

트랜잭션을 브로드캐스트하기 전에 가상 샌드박스에서 예상 사후 상태를 계산하고 검증하는 작업은 이러한 실행·추적 인프라를 활용해 결정론적으로 수행할 수 있는 접근법이다.

### 4.3 Delegation Framework와 결과 게이트의 결합

#### 4.3.1 Delegation Framework와 Caveat Enforcer의 역할

[Delegation Framework](https://docs.metamask.io/smart-accounts-kit/development/concepts/delegation/overview)는 스마트 계정(Smart Account)의 소유권(Ownership)과 실행 권한(Execution Rights)을 분리하여, 서드파티 대리인(Agent)이 한정된 권한 내에서 트랜잭션을 자율적으로 실행할 수 있도록 지원하는 인프라다.

위임된 권한의 온체인 집행은 Caveat Enforcer 스마트 컨트랙트가 통제한다. 대리인이 트랜잭션을 실행할 때, [Caveat Enforcer](https://docs.metamask.io/smart-accounts-kit/concepts/delegation/caveat-enforcers)는 `beforeHook`, `afterHook`, `afterAllHook` 훅(Hook) 인터페이스를 통해 트랜잭션 실행 전후의 권한 조건을 검사한다. 호출 대상 컨트랙트(Target Address), 허용된 함수(Selector), 유효 기간, 단일 지출 한도 등 사전에 명세된 규칙 중 하나라도 위반되면 전체 위임 상환(Redemption) 프로세스를 즉시 되돌려(Revert), 할당된 권한 밖의 트랜잭션 체결을 온체인 단계에서 차단한다. 결과 상태 검증 계층(Result State Verification Layer)은 이러한 온체인 권한 제어 구조를 우회하거나 대체하지 않는다. 기존 권한 조건을 충족하는 트랜잭션에도 사용자 승인 결과 정책을 독립적으로 적용하는 보완적 아키텍처로 기능한다.

#### 4.3.2 실험 A의 기준 구성과 결과 게이트 결합 검증

실험 A에서는 해당 권한 위임 인프라를 결과 상태 검증 계층의 차단 효과를 측정하기 위한 아키텍처 베이스라인으로 사용했다. 외부 네트워크를 포크하지 않은 격리된 로컬 환경(Anvil)에 실제 Delegation Framework와 6종의 Caveat Enforcer 구현체를 배포하여 고정된 베이스라인을 구성했다. 기존 Caveat Enforcer의 온체인 권한 검증 메커니즘은 수정 없이 유지하고, 런타임 트랜잭션 서명 및 브로드캐스트 직전에 결과 게이트(Result Gate)를 추가로 배치했다.

실증 과정에서는 초기 자산 잔액을 10,000 토큰으로 설정했다. 단일 거래의 잔액 감소량을 최대 500 토큰으로 제한하는 기존 Caveat 조건과, 실행 후 최소 9,700 토큰을 유지해야 하는 사용자 승인 결과 정책(`assetBalanceFloor`)을 동일한 트랜잭션 후보에 함께 적용했다. 500 토큰 전송 트랜잭션은 단일 지출 상한(최대 500 토큰 감소)이라는 권한 조건을 충족하므로 기존 Caveat 기반 경로에서는 온체인에서 체결이 허용됐다.

그러나 결과 게이트를 추가한 아키텍처에서는 오프체인 시뮬레이션으로 도출한 예상 사후 상태(9,500 토큰)가 사용자 승인 잔액 하한(9,700 토큰)을 위반함을 식별했다. 결과 게이트는 이를 `ASSET_BALANCE_FLOOR_VIOLATION`으로 판정하여 트랜잭션 서명 전에 실행을 즉시 중단했다. 이를 통해 결과 게이트가 기존 온체인 보안 계층과 함께 작동하며, 기존 권한 조건을 충족하더라도 사용자 승인 결과 정책을 위반하는 트랜잭션을 실행 전에 차단하는 추가 통제 효과가 입증됐다.

## 5. 실증 및 평가 (Evaluation)

### 5.1 실험 목적 및 결과

제안한 검증 계층을 평가하기 위해 세 가지 실험을 구성했다. 실험 A에서는 기존 권한 제한에 결과 검증을 추가했을 때의 차단 효과를, 실험 B에서는 승인된 정책과 실제 지갑 실행의 연결을, 실험 C에서는 검증 시점에 따른 처리 결과의 차이를 확인했다.

실험 A와 C에서는 게이트의 유무나 검증 위치에 따른 차이를 분리하기 위해 정책을 고정했으며, 실험 A의 정책과 승인 기록은 실험용 입력으로 구성했다. 실험 B에서는 기존 Sepolia 실행에서 보존된 자연어 요청과 정책 제안·승인 및 실행 기록을 사용했다.

#### 5.1.1 실험 A: 기존 권한 제한 대비 추가 차단 효과

실험 A는 기존 규칙을 충족하는 거래라도 승인된 잔액 하한을 위반하면 결과 게이트가 이를 차단하는지 확인하기 위해 수행했다. 정상 후보도 함께 평가하여 조건을 충족하는 거래가 게이트 추가 이후에도 실행되는지 확인했다. 평가한 정상 후보는 결과 게이트를 추가한 이후에도 실행됐다.

로컬 Anvil 환경에서 실제 Delegation Framework의 여섯 Caveat를 동일하게 적용하고, 결과 게이트의 유무만 달리했다. 시작 잔액은 10,000 토큰, 기존 규칙의 거래당 최대 감소량은 500 토큰이었다. 여기에 거래 후 최소 9,700 토큰을 유지해야 한다는 정책을 적용했다.

100 토큰 전송은 9,900 토큰을 남기므로 기존 조건과 잔액 하한을 모두 충족한다. 500 토큰 전송은 기존 감소 상한을 지키지만, 9,500 토큰만 남으므로 잔액 하한을 위반한다.

예상 사후 잔액은 시험용 블록체인에서 각 후보 거래를 먼저 실행하여 확인했다. 이때 실행 전 상태를 저장하고, 거래 처리 결과와 토큰 전송 내역 및 잔액을 확인한 뒤 실행 전 상태로 되돌렸다. 이 과정이 실험 A의 시뮬레이션에 해당한다. 이후 게이트가 있는 경로와 없는 경로를 각각 같은 상태에서 시작하여 사전 실행이 비교 결과에 영향을 주지 않도록 했다. 두 경로에서는 거래 내용뿐 아니라 정책·승인 기록과 위임된 권한도 동일하게 유지했다.

| 후보 | 기존 Caveat만 적용 | 동일 Caveat에 결과 게이트 추가 |
| --- | --- | --- |
| 100 토큰 전송 | 실행 성공, 잔액 9,900 토큰 | 실행 성공, 잔액 9,900 토큰 |
| 500 토큰 전송 | 실행 성공, 잔액 9,500 토큰 | 거절, 잔액 10,000 토큰 유지 |

정상 후보는 두 경로에서 모두 실행됐다. 반면 500 토큰 후보는 기존 경로에서는 실행됐지만, 결과 게이트를 추가한 경로에서는 잔액 하한 위반으로 전송 거래의 서명 전에 중단됐다. 사전 시뮬레이션과 상태 복원 이후의 실제 전송 단계에서 해당 후보의 서명·전송 호출은 모두 0회였으며, 시작 잔액이 유지됐다.

기존 감소 상한을 초과하는 501 토큰 후보는 블록체인 상태를 변경하지 않고 실행 가능 여부를 확인하는 별도 검사(`eth_call`)에서 기존 Caveat에 의해 거절됐다. 따라서 500 토큰 후보의 기존 경로 실행은 보호 규칙이 비활성화되어 발생한 결과가 아니라, 설정된 조건 안에 있는 거래가 허용된 결과였다. 이 비교에서 확인한 것은 고정된 기존 보호 구성에 별도의 잔액 하한을 추가로 집행한 효과다.

#### 5.1.2 실험 B: 승인 정책과 실제 Agent Wallet 실행의 연결

실험 B에서는 사용자 승인 결과 정책에 대한 판정이 실제 Agent Wallet의 실행과 중단으로 이어지는지 확인하기 위해 기존 Sepolia 직접 USDC 전송 기록을 검토했다. 새로운 LLM 호출이나 Sepolia 거래를 수행하지 않고, 기존 실행에서 보존된 자연어 요청과 정책 제안·승인 및 허용·거절 기록을 사용했다.

보존된 기록에는 자연어 원문, Gemini의 제안으로 기록된 구조화 정책, 정책의 이유와 가정, proposal hash, 해당 해시에 대한 `APPROVE` 확인 문자열, 후보 거래에 포함된 정책·승인 해시가 남아 있었다. 이를 통해 동일한 정책 제안이 승인 기록과 후보 평가에 연결됐는지 확인했다.

> 이 Sepolia Agent Wallet에서 USDC를 0.5개 이상 남겨줘.

승인된 정책은 거래 후 최소 0.5 USDC를 유지하는 `assetBalanceFloor`였다. 정상 후보는 잔액 1.0 USDC에서 0.1 USDC를 전송하도록 구성됐다. 해당 거래가 실행된 이후 잔액 0.9 USDC에서는 같은 정책을 적용하여 0.5 USDC 전송 후보를 평가했다.

| 후보 | 시작 잔액 | 전송량 | 예상 사후 잔액 | 결과 |
| --- | --- | --- | --- | --- |
| 정상 후보 | 1.0 USDC | 0.1 USDC | 0.9 USDC | 허용 후 실제 거래 성공 |
| 하한 위반 후보 | 0.9 USDC | 0.5 USDC | 0.4 USDC | Agent Wallet 실행 요청 전에 거절 |

정상 후보는 승인된 하한을 충족하여 결과 게이트를 통과했고, Agent Wallet 요청 이후 Guard Mode와 이메일 추가 인증을 거쳐 실행됐다. 성공한 거래의 영수증과 USDC 전송 이벤트를 확인했으며, 실행 당시 사후 잔액 0.9 USDC가 기록됐다. 하한 위반 후보는 예상 사후 잔액이 0.4 USDC로 계산되어 결과 게이트에서 중단됐고, 새로운 Agent Wallet 실행 요청과 거래 해시는 생성되지 않았다. Guard Mode의 이메일 추가 인증은 정상 후보가 결과 게이트를 통과한 이후의 지갑 실행 절차이며, 앞선 정책 승인 기록과는 구분된다.

두 후보는 동일한 정책을 사용하지만 정상 거래의 실행 전후로 시작 잔액이 달라졌으므로 같은 초기 상태를 사용한 대조 실험은 아니다. 따라서 실험 B는 결과 게이트의 추가 효과를 비교한 실험 A를 대신하지 않으며, 보존된 사용자 승인 결과 정책의 판정이 실제 Agent Wallet 요청의 실행과 중단으로 이어진 사례로 해석한다. proposal hash와 `APPROVE` 기록은 승인 대상 정책과 후보 거래의 연결을 확인하는 근거이지만, 해시 자체가 승인자의 암호학적 신원이나 정책 이해 여부를 증명하지는 않는다.

#### 5.1.3 실험 C: 검증 시점에 따른 처리 결과

실험 C에서는 거래를 검증한 뒤 잔액이 변경되는 상황에서 상태 확인 시점이 처리 결과에 미치는 영향을 평가했다. 로컬 Anvil 환경에서 검증이 없는 경로, 실행 요청 전에 검사하는 경로(`pre-submit`), 서명 직전에 상태를 확인하는 경로(`pre-sign`)를 비교했다. 이 비교에는 Delegation Framework의 Caveat나 Agent Wallet Guard를 적용하지 않았다.

시작 잔액은 시험용 토큰 1.0 GPTT, 최소 유지 잔액은 0.5 GPTT였다. 정상 후보는 0.1 GPTT 전송, 최초부터 하한을 위반하는 후보는 0.6 GPTT 전송으로 구성했다.

상태 변경 조건에서는 0.4 GPTT 전송 후보를 사용했다. 두 검증 위치 사이에 출금 권한을 미리 받은 외부 계정이 `transferFrom`으로 0.2 GPTT를 차감하도록 실행 순서를 고정했다. 각 비교는 저장한 상태를 복원하여 동일한 후보·정책·초기 잔액·논스·출금 허용량에서 수행했다.

| 조건 | 검증 없음 | 실행 요청 전 검사 (`pre-submit`) | 서명 직전 상태 확인 (`pre-sign`) |
| --- | --- | --- | --- |
| 0.1 GPTT 전송, 상태 유지 | 실행, 잔액 0.9 GPTT | 실행, 잔액 0.9 GPTT | 실행, 잔액 0.9 GPTT |
| 0.6 GPTT 전송, 최초부터 하한 위반 | 실행, 잔액 0.4 GPTT | 거절, 잔액 1.0 GPTT | 거절, 잔액 1.0 GPTT |
| 0.4 GPTT 전송 전 외부에서 0.2 GPTT 차감 | 실행, 잔액 0.4 GPTT | 실행, 잔액 0.4 GPTT | 거절, 잔액 0.8 GPTT |

정상 후보는 모든 경로에서 실행됐고, 최초부터 하한을 위반하는 후보는 두 검증 경로에서 모두 거절됐다. 차이는 검증 이후 잔액이 변경된 조건에서 나타났다.

`pre-submit` 경로에서는 1.0 GPTT에서 0.4 GPTT를 전송하면 0.6 GPTT가 남으므로 후보를 허용했다. 이후 외부 출금으로 잔액이 0.8 GPTT가 됐지만, 기존 허용 판정에 따라 거래가 실행되어 최종 잔액은 0.4 GPTT가 됐다.

`pre-sign` 경로에서는 현재 잔액이 앞선 검증 당시와 다르다는 사실을 탐지하고 `STALE_CAPTURED_CONTEXT`로 후보를 중단했다. 외부 출금만 반영되어 최종 잔액은 0.8 GPTT였다. 이 거절은 변경된 잔액으로 하한을 다시 계산한 결과가 아니라, 검증에 사용한 상태와 현재 상태의 불일치를 확인한 결과였다. 거절된 후보는 서명되거나 전송되지 않았다.

### 5.2 결과 및 해석

#### 5.2.1 결과 종합

실험 A에서는 동일한 여섯 Caveat와 서명된 위임을 유지한 상태에서 결과 게이트의 추가 효과를 비교했다. 100 토큰 전송은 기존 경로와 결과 게이트가 추가된 경로에서 모두 실행됐다. 500 토큰 전송은 기존 Caveat의 감소 상한을 충족하여 기존 경로에서는 실행됐지만, 예상 사후 잔액이 사용자 승인 결과 정책의 하한보다 낮아 결과 게이트가 추가된 경로에서는 거절됐다. 이 결과는 선택된 Caveat 구성을 통과하는 거래에도 별도의 잔액 하한을 추가로 적용할 수 있음을 보여준다.

실험 B에서는 자연어 요청으로부터 생성된 구조화 정책과 승인 기록을 실제 Sepolia Agent Wallet의 실행 경로에 연결했다. 정상 후보는 결과 게이트를 통과한 뒤 Guard Mode와 이메일 추가 인증을 거쳐 실행됐으며, 하한 위반 후보는 Agent Wallet 실행 요청 전에 중단됐다. 정책 판정이 내부 평가에 그치지 않고 실제 지갑 요청의 실행과 중단으로 이어질 수 있음을 확인했다.

실험 C에서는 검증에 사용한 상태가 실행 전에 변경되면 기존 허용 판정이 더 이상 유효하지 않을 수 있음을 확인했다. `pre-submit` 경로는 검증 이후 발생한 잔액 변경을 반영하지 못해 잔액 하한을 위반하는 거래를 실행했다. `pre-sign` 경로는 검증 당시 상태와 서명 직전 상태의 불일치를 탐지하고 기존 판정을 폐기했다. 결과 게이트의 방어 범위는 결과 정책의 내용뿐 아니라 상태 확인 시점과 집행 위치에도 영향을 받는다.

#### 5.2.2 결과의 해석 범위

평가 대상은 AI가 추론한 사용자의 숨은 목적이 아니라 사용자가 확인하고 승인한 결과 정책이다. LLM은 자연어 요청을 정해진 정책 형식으로 변환하며, 거래의 허용 여부는 승인된 정책과 예상 사후 상태를 비교하는 결정론적 평가기가 판정한다. 실험 결과는 승인된 정책이 사용자의 의도를 정확하게 표현한다는 전제에서 해석해야 한다.

실제 Agent Wallet 실행 경로에 적용한 정책은 특정 자산의 최소 잔액을 유지하는 `assetBalanceFloor`이다. 포트폴리오 전체의 가치 하한과 일정 기간의 누적 손실 상한은 저장된 실행 기록을 대상으로 오프라인에서 평가했다. 따라서 이를 다중 자산 가치와 누적 손실 정책을 실제 지갑의 전송 경계에서 집행한 결과로 해석할 수 없다.

실험 A는 로컬 환경에서 실제 Delegation Framework, 서명된 위임 및 여섯 Caveat를 적용한 비교 실험이다. 실험 B는 Sepolia Agent Wallet 주소의 직접 USDC 전송을 통해 정책 판정과 실제 지갑 요청의 연결을 확인한 사례다. 두 실험은 각각 기존 위임 보호와의 결합 가능성과 실제 Agent Wallet 실행 연결을 보여주지만, 원격 Agent Wallet에서 서명된 위임의 생성부터 실행까지 이어지는 단일 통합 경로를 검증한 것은 아니다.

### 5.3 Authorization–Intent Gap에 대한 결과 상태 검증 계층의 효과와 적용 범위

로컬 Delegation Framework 실험에서는 설정된 권한 조건을 충족하면서 사용자 승인 결과 정책은 위반하는 거래 후보가 나타났다. 동일한 Caveat와 서명된 위임 아래에서 평가한 정상 후보는 기존 경로와 결과 게이트가 추가된 경로에서 모두 실행됐지만, 잔액 하한을 위반한 후보는 결과 게이트에서 중단됐다. 이는 권한 조건의 충족과 예상 사후 상태의 승인이 서로 다른 판단이며, Authorization–Intent Gap을 다루려면 별도의 결과 상태 조건이 필요하다는 점을 보여준다.

이러한 추가 판단은 실제 Agent Wallet의 실행 통제와도 연결됐다. Sepolia 직접 USDC 전송에서는 결정론적 평가기가 자연어 요청에서 변환되어 승인된 구조화 정책을 적용했다. 정책을 충족한 후보는 결과 게이트를 통과한 뒤 Guard Mode와 이메일 추가 인증을 거쳐 실행됐고, 위반 후보는 새로운 Agent Wallet 실행 요청 전에 중단됐다. 결과 상태 검증 계층은 기존 지갑 보호 절차를 유지하면서, 승인된 정책과 예상 사후 상태의 불일치를 실행 전에 처리하는 보조 계층으로 작동했다.

검증 위치 비교에서는 이러한 효과가 판정에 사용한 상태의 유효성에 의존하는 것으로 나타났다. 상태가 유지된 조건에서는 `pre-submit`에서도 정책 위반 후보를 중단했으며, 로컬 `pre-sign` 경로는 뒤늦은 상태 변경을 탐지해 기존 허용 판정을 폐기했다. 따라서 명시적으로 승인된 `assetBalanceFloor`를 결과 게이트를 거치는 직접 토큰 전송에 적용하는 범위에서는, 권한 조건을 충족하지만 승인되지 않은 예상 사후 상태를 만드는 거래를 추가로 통제하는 기술적 적용 가능성이 확인됐다.

## 6. 한계 및 과제 (Limitations)

#### 6.1.1 적용 범위와 집행 경계

실제 Agent Wallet 실행 경로에 적용한 정책은 특정 자산의 최소 잔액을 유지하는 `assetBalanceFloor`이다. 포트폴리오 전체의 가치 하한과 24시간 누적 손실 상한은 저장된 실행 기록을 대상으로 오프라인에서 평가했다. 따라서 이를 다중 자산 가치와 누적 손실 정책을 실제 지갑의 전송 경계에서 집행한 결과로 해석할 수 없다.

실험 A에서는 로컬 환경에서 실제 Delegation Framework와 서명된 위임 및 여섯 Caveat를 적용했다. 실험 B에서는 Sepolia Agent Wallet 주소의 직접 USDC 전송을 통해 사용자 승인 결과 정책의 판정과 실제 지갑 요청의 연결을 확인했다. 두 결과는 각각 기존 위임 보호와의 결합 가능성과 실제 Agent Wallet 실행 경로와의 연결을 보여주지만, 원격 Agent Wallet에서 서명된 위임의 생성부터 실행까지 이어지는 단일 통합 경로를 검증한 것은 아니다.

결과 게이트는 Agent Wallet을 호출하는 애플리케이션 경로에 통합되어 있다. 따라서 실험 결과는 해당 경로를 거친 거래에 대한 집행 효과를 보여주며, 결과 게이트가 통합되지 않은 지갑 실행 경로에도 동일한 정책이 적용됨을 의미하지는 않는다.

#### 6.1.2 검증과 실행 사이의 상태 변경

현재 구현에서는 후보 거래가 생성되고 예상 사후 상태가 계산된 뒤, Agent Wallet에 실행을 요청하기 전인 `pre-submit` 위치에 결과 게이트를 배치했다. 이 위치에서는 검증 시점에 이미 사용자 승인 결과 정책을 위반하는 후보를 지갑 실행 요청 전에 중단할 수 있다.

그러나 판정 결과는 검증에 사용한 상태가 실행 시점까지 유지된다는 전제에 의존한다. 거래를 검사한 뒤 잔액이나 논스 등 관련 상태가 변경되면, 앞서 계산한 예상 사후 상태가 실제 실행 시점의 상태를 반영하지 못할 수 있다. 실험 C에서는 `pre-submit` 검증 이후 외부 계정이 잔액을 변경하자 기존 허용 판정이 그대로 사용되어 잔액 하한을 위반하는 결과가 발생했다. 이는 검증과 실행 사이의 시간 차이에서 발생하는 TOCTOU(Time-of-Check to Time-of-Use) 문제를 보여준다.

로컬 `pre-sign` 경로에서는 검증 당시 상태와 서명 직전 상태가 달라졌음을 확인하고 기존 판정을 폐기했다. 이는 변경된 상태를 기준으로 정책을 다시 계산한 결과가 아니라, 기존 판정의 전제가 더 이상 유효하지 않다고 판단한 결과다. 따라서 상태 확인을 서명 경계에 가깝게 배치하면 상태가 변경됐는데도 이전 허용 판정이 사용되는 범위를 줄일 수 있다.

다만 `pre-sign` 경로는 검증 위치를 비교하기 위해 로컬에서 구성한 통제 경로이며, 실제 Agent Wallet 내부에 통합된 기능은 아니다. 또한 서명 직전에 상태를 확인하더라도 서명 이후 트랜잭션이 블록에 포함될 때까지 상태나 거래 순서가 달라질 가능성은 남는다. 그러므로 `pre-sign` 확인만으로 예상 사후 상태와 실제 온체인 결과의 일치를 원자적으로 보장할 수는 없다.

실행 직전의 재시뮬레이션과 상태 재확인, 검증 결과의 유효기간 제한은 검증과 실행 사이의 간격을 줄일 수 있다. 결과 상태를 더 강하게 보장하려면 정책 조건을 온체인에서 함께 집행하거나 검증과 실행을 하나의 원자적 과정으로 결합하는 구조가 추가로 필요하다.

#### 6.1.3 정책과 실행 환경의 신뢰 전제

오프체인 검증은 현재 상태와 시뮬레이션 결과를 제공하는 실행 환경을 신뢰한다. 실험 A와 C는 외부 체인을 포크하지 않은 격리된 로컬 환경에서 수행했지만, Sepolia 사례와 실제 운영 환경에서는 외부 RPC 노드가 제공하는 블록 상태와 거래 결과에 의존한다. RPC가 오래된 상태나 부정확한 결과를 반환하면 결과 게이트도 잘못된 예상 사후 상태를 기준으로 판정할 수 있다.

서로 독립된 RPC 응답을 비교하거나 상태를 직접 검증하는 노드를 사용하고, 판정에 사용한 블록 번호와 상태를 기록하면 이러한 의존성을 줄일 수 있다. 다만 여러 RPC를 사용한다는 사실만으로 응답의 정확성이 보장되지는 않으므로, 응답이 일치하지 않을 때 거래를 중단할 기준이 별도로 필요하다.

정책 생성과 승인 과정에도 신뢰 전제가 존재한다. LLM이 자연어 요청의 자산, 단위 또는 임계값을 잘못 변환할 수 있으며, 사용자가 변환 오류를 확인하지 못하고 정책을 승인할 가능성도 있다. 결정론적 평가기는 사용자 승인 결과 정책을 일관되게 집행하지만, 해당 정책이 사용자의 원래 의도를 정확히 표현하는지까지 판단하지는 않는다. 따라서 승인 단계에서는 대상 자산과 단위 및 임계값을 명확히 표시하고, 지원하지 않는 표현이나 모호한 요청을 자동으로 적용하지 않아야 한다.

실험 B에는 자연어 요청, 구조화 정책, proposal hash, 해당 해시에 대한 `APPROVE` 확인 문자열과 후보가 참조한 정책·승인 해시가 보존되어 있다. 이 기록은 동일한 정책 제안이 승인 기록과 후보 평가에 연결됐는지 확인하는 근거다. 그러나 해시 자체는 승인자의 암호학적 신원이나 정책에 대한 이해를 증명하지 않는다. 정상 후보 실행 과정의 Guard Mode와 이메일 추가 인증도 결과 게이트를 통과한 이후의 지갑 실행 절차이므로, 앞선 정책 승인 행위의 인증과는 구분된다. 따라서 실험 B의 승인 증거는 보존된 승인 기록이 후보 판정과 실행 경로에 적용됐다는 범위로 해석해야 한다.

다중 자산의 포트폴리오 가치처럼 외부 가격이 필요한 정책으로 범위를 확장하면 가격 정보의 출처와 갱신 시점도 판정에 영향을 준다. 가격 오라클의 지연이나 오류가 발생하면 동일한 자산 상태가 서로 다른 가치로 평가될 수 있다. 가격 기반 정책은 실제 전송 경로에 적용하지 않았으므로 실시간 집행 가능성은 별도로 검증해야 한다.

검증 요청의 복잡도와 처리량도 운영 단계에서 확인해야 한다. 실험은 단일 자산의 잔액 하한을 중심으로 수행했기 때문에 복잡한 다중 호출이나 다수 자산의 가격 계산이 처리 시간과 자원 사용량에 미치는 영향은 측정하지 않았다. 정책 형식과 호출 깊이, 실행 시간 및 요청 빈도에 대한 제한은 실제 운영 조건을 기준으로 추가 검증해야 한다.

#### 6.1.4 실험 환경과 증거의 해석 범위

실험 결과를 다시 확인할 수 있도록 코드 버전과 실행 환경을 고정했다. Delegation Framework는 커밋 `197463b4aba3409adef1df544dabafc3636ee82d`를 사용했으며, 신규 실험 환경은 Node v24.14.1, viem 2.55.11, Anvil·Forge 1.5.1-stable로 기록했다. 기존 오프라인 평가 환경은 Python 3.13.12와 Pydantic 2.13.4를 사용했다.

증거의 성격도 실험별로 구분했다. 실험 A와 C는 로컬에서 새로 수행한 비교 실험이며, 같은 시작 조건을 복원해 각 경로를 평가했다. 실행된 후보는 거래 영수증과 토큰 전송 이벤트 및 사후 상태로 실행 여부를 확인했다. 거절된 후보는 해당 후보의 서명·전송 호출이 없었는지 확인하고, 외부 출금에 따른 상태 변경은 후보 실행의 영향과 구분했다. 실험 B는 기존 Sepolia 실행에서 보존된 허용·거절 기록을 재검토했으며, G3는 저장된 실행 기록을 대상으로 다시 수행한 오프라인 평가다. 이 자료들을 하나의 통합 실행 결과로 해석하지 않는다.

Sepolia 정상 거래는 온체인 영수증과 호출 내용 및 토큰 전송 이벤트를 다시 확인했다. 실행 당시의 사후 잔액 0.9 USDC는 보존된 기록에 포함되어 있지만, 이후 공개 RPC 조회에서는 해당 블록의 과거 잔액을 별도로 재도출하지 못했다. 따라서 당시 보존된 사후 잔액과 이후 온체인에서 다시 확인한 항목을 구분한다. 하한 위반 후보는 새로운 Agent Wallet 요청과 거래 해시가 생성되지 않은 기록을 통해 실행 전 중단을 확인했다.

저장된 파일은 보존된 기준 해시와 대조하여 내용의 동일성을 확인했다. 이러한 해시 검사는 기록의 변경 여부를 점검하는 수단이며, 파일에 포함된 모든 설명이나 사용자 승인 행위를 외부에서 독립적으로 인증한다는 의미는 아니다. 실험 환경과 코드 버전, 실행·거절의 판정 기준을 기록하여 결과의 확인 범위를 명시했다. 상세 실행 기록과 원본 증거는 실험 과정에서 보존했으며, 본문에는 결과 해석에 필요한 항목을 제시한다.

이러한 한계를 고려하면 결과 게이트는 기존 권한 조건을 통과한 거래 중 사용자 승인 결과 정책을 위반하는 후보를 추가로 걸러내는 보조 안전 계층으로 볼 수 있다. 향후에는 검증 위치를 실제 서명 경계에 더 가깝게 통합하고, 정책 승인 기록의 인증 수준과 외부 상태 정보의 처리 기준 및 복잡한 정책의 실행 비용을 추가로 검증할 필요가 있다.

## 7. 결론 (Conclusion)

결과 상태 검증 계층은 기존 Agent Wallet의 권한 보호를 유지하면서, 거래 후보의 예상 사후 상태를 사용자 승인 결과 정책과 비교해 실행 여부를 추가로 판정한다. LLM은 자연어 요청을 구조화된 정책으로 변환하는 역할을 맡고, 사용자 승인 이후의 거래 판정은 결정론적 평가기가 수행한다.

실험에서는 기존 Caveat의 권한 조건을 충족하더라도 승인된 잔액 하한을 위반하는 후보는 결과 게이트에서 중단됐으며, 평가한 정상 후보는 실행됐다. Sepolia Agent Wallet의 직접 USDC 전송에서도 정책 판정이 실제 지갑 요청의 실행과 중단으로 이어졌다. 다만 검증 이후 상태가 변경되면 pre-submit의 기존 허용 판정으로 하한 위반을 막지 못했고, 로컬 pre-sign 경로에서는 상태 불일치를 탐지해 후보를 중단했다.

이 결과는 결과 게이트를 거치는 직접 토큰 전송에 assetBalanceFloor를 적용한 범위에서, 권한 조건과 사용자 승인 결과 정책 사이의 불일치인 Authorization–Intent Gap을 줄일 수 있음을 보여준다. 후속 과제는 실제 서명 경계에서의 통합과 상태 재검증, 다중 자산·누적 손실 정책의 실시간 집행을 검증하는 것이다. 실제 온체인 결과를 더 강하게 보장하기 위한 원자적 집행 구조도 검토할 필요가 있다.
