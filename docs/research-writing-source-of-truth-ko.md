- **추론됨:** 직접 관측값과 다른 증거를 결합해 복원한 값이다.
- **계획됨:** 아직 구현 또는 검증되지 않았다.

## 1. 연구의 목적과 핵심 질문

이 글은 개발한 프로젝트를 소개하는 제품 글이 아니다.

AI 에이전트 지갑에서 권한상 허용된 거래가 사용자의 실제 의도와 다른 결과를 만들 수 있는 문제를 분석하고, 이를 완화하기 위한 **결과 상태 기반 마지막 보호장치**를 제안·검증하는 proof-of-concept 연구다.

핵심 질문은 다음과 같다.

> AI 에이전트 지갑의 방어 기준을 “설정된 권한 정책상 허용된 호출인가?”에서 “실행 결과가 사용자가 승인한 상태 불변식을 만족하는가?”까지 확장할 수 있는가?

이를 이 연구에서는 **Authorization–Intent Gap**이라고 부른다.

> 시스템이 설정된 권한 정책에 따라 허용한 행동과 사용자가 별도로 승인한 결과 상태 사이의 간극

이 용어는 실제 사용자의 심리적 의도를 자동으로 알아냈다는 뜻이 아니다. 실험에서는 사용자가 검토·승인한 결과 정책을 의도의 조작적 표현으로 사용한다.

## 2. 위협 모델과 연구 범위

### 2.1 가정하는 실행 경로

- 사용자는 제한된 정책 스키마로 변환된 결과 정책을 검토하고 승인한다.
- 에이전트와 클라이언트는 제안된 통합 경로를 사용한다.
- 예정 거래는 브로드캐스트 전에 시뮬레이션된다.
- 결정론적 검증기는 승인된 정책과 시뮬레이션된 사후 상태를 비교한다.
- 검증을 통과한 거래만 통합 애플리케이션의 지갑 확인 단계로 전달된다.

### 2.2 방어하려는 문제

- 설정된 권한·허용목록·한도·기간 조건을 통과하지만, 별도로 승인된 자산 하한이나 누적 손실 정책을 위반하는 거래
- 단일 호출의 명목 수량만 보면 허용되지만 여러 거래가 합쳐져 원치 않는 결과를 만드는 시퀀스
- 자연어 의도와 런타임 판정 사이에 검증 가능한 정책 표현이 없는 문제

### 2.3 범위 밖의 공격과 한계

- 사용자가 제안 경로를 우회해 직접 거래를 전송하는 경우
- 에이전트가 다른 RPC·지갑·클라이언트에서 거래를 브로드캐스트하는 경우
- 지갑 또는 스마트컨트랙트 내부의 네이티브 집행
- 개인키 탈취, 지갑 자체 손상, 합의 실패, 체인 재구성 등 기반 계층의 공격
- 프롬프트 인젝션·세션 오류 자체의 제거
- 모든 토큰, DEX, 브리지, 멀티체인, 수수료·MEV 효과의 완전한 모델링

따라서 **마지막 보호장치**는 전 세계의 모든 전송 경로에서 강제되는 절대적 마지막 단계가 아니다. 이 연구가 통합하고 신뢰하는 애플리케이션 실행 경로 안에서, 지갑 확인 및 브로드캐스트 직전에 동작하는 마지막 게이트를 뜻한다.

## 3. 핵심 솔루션

사용자의 자연어 의도를 LLM이 제한된 정책 불변식으로 변환하고, 거래 실행 직전에 시뮬레이션된 사후 상태가 그 불변식을 만족하는지 결정론적 코드로 검사한다.

역할은 다음처럼 분리한다.

- **LLM:** 자연어 의도를 제한된 불변식 스키마로 번역하는 컴파일러
- **사용자:** 변환된 정책과 가정·근거를 검토·수정하고 정확한 제안을 승인
- **로컬 검증기:** 스키마, 허용된 체인·지갑·토큰, 수치 단위, 정책 해시를 검증
- **시뮬레이터:** 예정 거래의 사후 상태를 계산
- **결정론적 정책 평가기:** 승인된 불변식에 따라 허용 또는 거부를 판정
- **기존 Agent Wallet 보안:** 권한, Caveat, 한도, 허용목록, 위협 탐지 등 기존 보호 계층
- **제안 계층:** 통합 실행 경로의 브로드캐스트 직전에 결과 상태를 추가 검사

핵심 원칙은 다음과 같다.

> LLM은 컴파일러이고, 결정론적 코드가 심판이다.

이 계층은 기존 Agent Wallet 보안을 대체하지 않는다. 기존 보호 계층과 함께 사용되는 추가 방어선이다.

## 4. 정책 범위

현재 정책 범위를 라이브 실행 경로와 오프라인 연구 경로로 분리해 서술한다.

### 4.1 실제 지갑 실행 경로

현재 실제 지갑 실행 경로에서 지원하는 정책은 한 종류다.

- `assetBalanceFloor`: 지정 자산의 거래 후 잔액이 승인된 최소값 이상이어야 한다.

### 4.2 오프라인 연구·평가 경로

포트폴리오 관련 네 종류의 불변식은 오프라인 연구·평가 경로에만 존재한다. 이들을 실제 지갑 실행 경로에 모두 통합했다고 쓰지 않는다.

개별 정책의 정확한 명칭·의미·평가 방식은 기준 커밋의 스키마와 평가기 코드를 인용해 작성한다. 글에서는 라이브 `assetBalanceFloor`와 오프라인 포트폴리오 불변식이 동일한 실행 파이프라인에서 검증된 것처럼 합치지 않는다.

## 5. RQ1 — 기존 보호 체계의 표현력 한계

### 5.1 핵심 질문

> 선택한 Delegation Framework Caveat 구성으로 표현하지 못하는 결과 상태는 무엇이며, 그 부재는 어떤 허용된 손실 시퀀스를 가능하게 하는가?

### 5.2 분석 대상

- MetaMask Agent Wallet과 Delegation Framework가 제공하는 기존 보호 개념
- 실험에 고정한 여섯 개 Caveat의 동작
- 허용 주소, 허용 메서드, 건별·기간별 한도, 유효기간, 잔액 차분 검사
- 기존 Caveat가 정상 작동한다는 baseline
- 여섯 Caveat를 각각 통과하면서 누적 자산 고갈이 발생하는 G3 시퀀스
- 자산 잔액 하한, 포트폴리오 가치 하한, 거래 간 누적 손실 상한 같은 결과 정책의 필요성

### 5.3 반드시 지킬 표현

기존 보호를 모두 `정적 검사`라고 부르지 않는다. Delegation Framework의 일부 Enforcer는 기간별 누적 상태를 사용하고, 실행 후 hook에서 잔액 차분을 검사한다.

정확한 한계는 다음과 같이 쓴다.

> 선택한 Caveat 구성은 주소·메서드·명목 수량·기간별 사용량·개별 redemption 전후의 특정 잔액 차분을 제한할 수 있다. 그러나 이 실험의 고정된 여섯 Caveat만으로는 여러 거래에 걸친 포트폴리오 가치 하한이나 별도로 정의한 누적 손실 정책을 직접 표현하지 못한다.

`기존 보호를 모두 통과했다`고 쓰지 않는다. 다음과 같이 범위를 고정한다.

> 고정된 Delegation Framework 커밋에서 실험에 구성한 여섯 Caveat를 모두 통과했다.

이는 MetaMask Agent Wallet의 모든 위협 탐지, Blockaid, MEV 보호, Transaction Protection 또는 운영 환경 전체를 통과했다는 뜻이 아니다.

### 5.4 G3 실험의 의미

현재 G3 trace는 다음의 구성된 반례를 제공한다.

- 초기 잔액: 10,000 USDC
- 전송 단위: 500 USDC
- 성공한 단계: 20회
- 최종 잔액: 0 USDC
- 각 단계: 실험에 구성한 여섯 Caveat를 통과
- 총 명목 유출: 10,000 USDC

G3가 실제 사용자의 숨은 의도를 증명한다고 쓰지 않는다. G3는 다음만 보여준다.

> 구성한 권한 정책은 이 누적 고갈 시퀀스를 허용하지만, 별도로 명시·승인한 결과 정책은 같은 시퀀스를 거부할 수 있다.

### 5.5 RQ1 결론

> 기존 권한 검사가 고장 난 것이 아니라, 선택한 권한 구성의 표현 범위 밖에 별도로 승인할 수 있는 결과적 안전 속성이 남는다.

이 결론을 모든 Agent Wallet 또는 모든 Caveat 조합에 대한 일반 명제로 확대하지 않는다.

## 6. RQ2 — 자연어 의도를 검증 가능한 불변식으로 변환

### 6.1 핵심 질문

> 사용자의 자연어 의도를 검증 가능한 불변식으로 만들기 위해 LLM은 어떤 제한된 역할을 맡아야 하며, 그 방식의 장점과 한계는 무엇인가?

### 6.2 비교할 접근

- 개발자가 정책을 직접 작성
- 사용자가 구조화된 조건을 직접 입력
- LLM이 거래 위험을 직접 판정
- LLM이 임의의 실행 코드를 생성
- LLM이 제한된 정책 스키마로만 컴파일

다섯 접근의 장단점 비교는 **정성적 설계 비교**로 제시한다. 아래 60개 벤치마크는 선택한 제한 스키마 컴파일러의 한 실행 결과일 뿐, 다른 접근보다 일반적으로 우월하거나 실제 사용자 의도를 정확히 이해한다는 증거가 아니다.

고정된 60개 한국어 사례를 Gemini `gemini-3.5-flash-lite`로 실행했다. 58개는 엄격한 로컬 출력 계약을 통과했고 2개는 계약 위반으로 제안을 만들지 않고 fail-closed 처리됐다. 실패를 비승인으로 포함한 운영 지표는 support classification accuracy `0.9667`, precision `1.0`, recall `0.9583`, false-positive rate `0.0`, exact invariant accuracy `0.9667`이었다. 혼동행렬은 TP 46, TN 12, FP 0, FN 2다.

엄격한 provider-output coverage는 `58/60`이므로 완료된 60개 strict-output 벤치마크라고 쓰지 않는다. `0.0` false-positive rate도 이 고정 데이터셋의 한 실행에만 해당하며 일반적인 low false positive 주장으로 확대하지 않는다. 결과 파일은 모델·프롬프트·데이터셋·설정 해시와 실패 상태를 보존한다.

### 6.3 선택한 구조

```text
자연어 의도
→ 제한된 LLM 구조화 출력
→ 로컬 스키마 및 지원 범위 검증
→ 사용자 검토·수정
→ 정확한 제안 해시 승인
→ 결정론적 런타임 검증
```

- LLM은 체인·지갑·토큰을 임의로 선택할 수 없다.
- 미지원·혼합·모호한 요청과 모델 실패는 정책을 만들지 않고 fail-closed 처리한다.
- 정책 또는 승인 대상 내용이 바뀌면 새로운 해시가 생성되고 기존 승인은 무효화된다.
- 런타임 허용 여부는 LLM이 아니라 결정론적 코드가 판정한다.

### 6.4 승인 해시의 정확한 의미

정확한 해시 승인은 승인 대상의 **무결성과 결합성**을 제공한다. 즉, 사용자가 승인한 제안과 런타임에 사용된 제안이 같은지 확인하는 데 도움이 된다.

하지만 다음을 자동으로 보장하지는 않는다.

- 사용자가 정책의 의미를 실제로 이해했다는 것
- 승인 주체의 법적·암호학적 신원 인증
- 자연어 의도가 완전하고 모호하지 않다는 것
- LLM이 사용자의 진짜 의도를 알아냈다는 것

현재 UI는 정확한 승인 문구를 화면에 표시하고 입력란에 미리 채운다. 따라서 `사용자가 해시를 직접 입력해 의미를 확인했다`고 쓰지 않고, `표시된 정확한 승인 문구를 제출했다`고 쓴다. UI가 의도·정책·근거·가정을 함께 보여주는 것과 사용자의 실질적 이해는 별개의 문제다.

### 6.5 RQ2 결론

> LLM을 거래 안전성의 최종 판정자가 아니라 제한된 검증 명세의 컴파일러로 배치하면, 자연어 입력과 결정론적 런타임 평가를 연결하고 계약 위반 출력을 비승인으로 처리할 수 있다. 고정된 60개 사례의 운영 평가는 이 제한된 실행 가능성을 뒷받침하지만, 엄격한 출력 계약 통과율은 58/60이었고 번역 정확도와 사용자 이해도의 일반화에는 별도 평가가 필요하다.

## 7. RQ3 — 실행 직전 결과 상태 검증과 테스트

RQ3는 서로 다른 두 실험 경로로 분리한다. 둘을 하나의 라이브 통합 실험처럼 서술하지 않는다.

### 7.1 RQ3-A: 오프라인 누적 손실 평가

핵심 질문은 다음과 같다.

> 오프라인 평가 경로의 결과 불변식이 RQ1의 G3 누적 손실 후보를 거부하고, 동일 조건에서 정책 범위 안의 정상 후보를 허용할 수 있는가?

G3 누적 손실 시퀀스와 거부 평가에 더해, 같은 fork·oracle·초기 상태·정책을 사용하고 전송 횟수와 수량만 정책 범위 안으로 낮춘 **구성된 대응 정상 후보**가 별도 아티팩트로 존재한다. 정상 후보는 300 USDC씩 5회 전송하는 반사실적 control이며 실제 G3 실행에서 관측된 거래가 아니다. 최종 가치는 `27,479.1354361 USD`, 누적 손실은 `1,499.65128 USD`로 두 불변식을 모두 만족해 허용된다.

### 7.2 RQ3-B: Sepolia 라이브 `assetBalanceFloor` 실행

핵심 질문은 다음과 같다.

> 실제 애플리케이션 실행 경로에서 시뮬레이션된 거래 후 자산 잔액이 승인된 `assetBalanceFloor`를 만족할 때 거래를 허용하고, 위반할 때 브로드캐스트 전에 거부할 수 있는가?

보호장치의 의도된 위치는 다음과 같다.

```text
기존 권한·한도·허용목록 검사
→ 실행 전 거래 시뮬레이션
→ 승인된 결과 상태 불변식 검사
→ 컨텍스트 재검증
→ 지갑 확인 및 거래 전송
→ 영수증과 사후 상태 검증
```

현재 구현은 애플리케이션 수준의 게이트다. 지갑·컨트랙트 네이티브 집행이라고 부르지 않는다.

### 7.3 현재 Sepolia 성공 사례

- 네트워크: Ethereum Sepolia
- chain ID: `11155111`
- 자산: Circle Sepolia USDC
- 토큰 주소: `0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238`
- 송신자: MetaMask Agent Wallet `0xb11539d7b6423c4523e1fba35953154b6b393df9`
- 수신자: `0x9f85d965258624053734d8caea00dc3f452f3c27`
- 승인 하한: 0.5 USDC
- 전송 전 잔액: 1 USDC
- 전송 수량: 0.1 USDC
- 검증된 전송 후 잔액: 0.9 USDC
- 거래 해시: `0xaf7566c59d0b10c3983f2478088ac31df165b1acaf1b6084acacd96d08d4f500`
- 블록: `11628030`

공개 Sepolia 기록에서 다음을 확인했다.

- 거래 성공 상태
- 송신자와 USDC 컨트랙트 대상
- `transfer` calldata의 수신자와 100,000 base units
- 해당 거래 영수증의 Transfer 이벤트
- 거래 후 송신자 잔액 900,000 base units

실행 경로는 실제 Gemini 구조화 출력, 정확한 proposal hash 승인, 공개 RPC `eth_call`, nonce·잔고 재검증, Agent Wallet CLI 전송 요청, Guard Mode의 이메일 MFA, 브로드캐스트, 영수증과 정확한 transaction 필드 및 Transfer 이벤트·사후 잔액 검증을 순서대로 통과했다. candidate hash는 `0x2ef30f41600d6ac40dd4be5c44aecfe29315951eac0149c80ab719161f8786e9`다.

다음 값은 온체인만으로 독립 검증할 수 없으므로 해시 결합된 오프체인 번들로 보존한다.

- 자연어 의도와 LLM 출력
- 승인 하한 0.5 USDC
- proposal·approval·candidate·decision 해시
- Agent Wallet 요청 ID와 MFA 승인 후 `BROADCASTED` 상태

이것은 Agent Wallet이 `assetBalanceFloor`를 네이티브 정책으로 집행했다는 뜻이 아니다. 제안한 애플리케이션 게이트가 결과 상태를 검사한 뒤 정확한 거래를 Agent Wallet에 전달했고, Agent Wallet은 자신의 Guard Mode와 MFA를 별도로 집행했다. 또한 direct ERC-20 전송이며 서명된 Delegation Framework redemption 실험은 아니다.

과거 거래 `0xe6d1f176…5564`와 40→39 USDC 기록은 보조 역사 자료로 남기지만, 원래의 오프체인 proposal·approval·plan hash가 보존되지 않아 현재 주 성공 증거로 사용하지 않는다.

### 7.4 RQ3에 추가로 필요한 최소 증거

동일한 application-level Sepolia 경로에서 39 USDC 잔고에 20 USDC 하한을 승인하고 25 USDC 전송을 계획한 라이브 거부 아티팩트를 추가했다. 공개 RPC 시뮬레이션의 예상 사후 잔액은 14 USDC였고, 결정론적 판정은 `ASSET_BALANCE_FLOOR_VIOLATION`으로 거부했다. `walletRequest: null`, `txHash: null`, `broadcastAttempted: false`가 같은 증거 번들에 기록된다.

별도로 현재 로그인된 MetaMask Agent Wallet 주소를 정책의 wallet과 실행 sender에 결합하는 direct ERC-20 실행 경로를 구현했다. 1 USDC 잔고에서 0.5 USDC 하한을 승인하고 0.1 USDC를 보내는 후보는 RPC 시뮬레이션과 nonce·잔고 재검증을 통과한 뒤 Agent Wallet CLI와 이메일 MFA를 거쳐 브로드캐스트됐고, 영수증·exact calldata·Transfer·0.9 USDC 사후 잔액까지 확인됐다.

### 7.5 RQ3 결론

> 제한된 실험 범위에서 오프라인 결과 상태 평가가 구성된 누적 손실 후보를 거부하고 대응 정상 후보를 허용했다. Sepolia의 애플리케이션 수준 `assetBalanceFloor` 경로는 하한 위반 후보를 거래 생성 전에 거부했으며, 하한을 유지하는 direct ERC-20 후보는 실제 MetaMask Agent Wallet과 MFA를 거쳐 브로드캐스트된 뒤 영수증·Transfer·사후 잔액까지 검증됐다.

## 10. 최소 논문 증거 세트

최종 글에는 가능하면 같은 schema의 네 가지 증거 번들을 제시한다.

1. G3 누적 손실 후보 거부
2. G3와 대응되는 정상 후보 허용
3. Sepolia `assetBalanceFloor` 정상 거래 허용 및 성공
4. `assetBalanceFloor` 위반 예정 거래 거부 및 무브로드캐스트

각 번들은 `입력 → 승인 정책 → 실행 후보 → 시뮬레이션 → 결정 → 브로드캐스트 여부 → 사후 증거`의 연결을 검토할 수 있어야 한다.

## 11. 최종 연구 포지션

이 연구는 완성형 Agent Wallet 보안 시스템의 일반적 안전성을 증명하지 않는다.

AI 에이전트 지갑에서 결과 상태 기반 마지막 보호장치가 왜 필요한지 구성된 반례로 설명하고, 제한된 오프라인 및 Sepolia 범위에서 기술적 실행 가능성을 확인하는 proof-of-concept 연구다.

### 주장하지 않을 내용

- Agent Wallet 자체의 고유 취약점을 증명했다는 주장
- 프롬프트 인젝션이나 세션 오류 자체를 제거한다는 주장
- 기존 보안 계층을 대체한다는 주장
- 모든 정상 거래를 오탐 없이 허용한다는 주장
- 모든 공격 거래를 차단한다는 주장
- 지갑·컨트랙트 수준의 네이티브 집행을 구현했다는 주장
- 모든 Agent Wallet 보호 계층을 실험에서 통과했다는 주장
- 실제 사용자의 숨은 의도를 알아내거나 증명했다는 주장
- 대규모 오차행렬 또는 Low False Positive를 검증했다는 주장
- 오프라인 포트폴리오 4종 불변식을 현재 라이브 지갑 경로에서 집행한다는 주장

## 12. 문장 작성 규칙

### 사용해도 되는 표현

- `실험에 구성한 여섯 Caveat를 통과했다.`
- `별도로 승인된 결과 정책이 구성된 누적 손실 후보를 거부했다.`
- `애플리케이션 실행 경로의 브로드캐스트 직전 게이트다.`
- `정확한 해시 승인은 승인 대상의 무결성과 결합성을 제공한다.`
- `Sepolia에서 하한을 유지하는 비경계 정상 거래가 성공했다.`
- `제한된 proof-of-concept 범위에서 실행 가능성을 확인했다.`

### 사용하면 안 되는 표현

- `기존 보호는 모두 정적 검사다.`
- `Agent Wallet의 모든 보안을 통과했다.`
- `G3가 사용자의 실제 의도를 증명한다.`
- `해시 승인이 사용자의 이해와 신원을 보장한다.`
- `지갑 또는 컨트랙트가 정책을 강제한다.`
- `포트폴리오 불변식이 실제 Sepolia 거래를 막았다.`
- `현재 성공 거래가 하한 정책의 차단 효과를 증명한다.`
- `낮은 오탐률 또는 높은 정확도를 검증했다.`

## 13. 외부 사실 사용 시 주의점

MetaMask Agent Wallet 공개 시점은 하나의 날짜로 단순화하지 않는다.

- 2026-06-08: 출시 및 Early Access 발표
- 2026-08-06: `now live` 소개 게시물

Transaction Protection의 최대 10,000달러 보호 문구는 자격 요건·약관·제외 조건이 있는 운영상 보상 프로그램이다. 이를 Authorization–Intent Gap이나 누적 손실의 직접 증거로 사용하지 않고, 기존 보안과 잔여 위험을 설명하는 배경으로만 사용한다.

모델명은 현재 구현과 공식 문서를 함께 확인한다. 기준일의 구현은 `gemini-3.5-flash-lite`를 사용한다. 제출 시점에 모델·문서가 바뀔 수 있으므로 고정 실행 기록을 우선한다.

## 15. 최종 메시지

> AI 에이전트 지갑의 안전 기준은 권한을 세분화하는 데 머물지 않고, 실행 결과가 사용자가 명시적으로 승인한 상태를 유지하는지 확인하는 방향으로 확장될 수 있다. 자연어 의도를 제한된 불변식으로 컴파일하고 이를 통합 실행 경로의 브로드캐스트 직전에 결정론적으로 검증하는 계층은 기존 보호 체계를 보완하는 마지막 방어선이 될 수 있다.
