# Phase 1 합격 기준 — 8/13 결정 게이트

기간 2026-08-08 ~ 08-13. **구현 전에 이 기준을 먼저 확정했다.** 구현이 끝난 뒤
기준을 완화하지 않는다.

## 목표

baseline 방어 계층을 **전부 통과**하면서 사용자에게 손해인 실행 트레이스 **1건**
(누적 손실 클래스)을 포크 환경에서 실제로 실행하고 로그로 남긴다.

기획안 8/13 게이트: 이 트레이스를 한 건도 못 얻으면 주제를 재설계한다.

## 왜 누적 손실을 먼저 하는가

셋 중 환경 구축 부담이 가장 작다. 얕은 풀 시딩도, perp/렌딩 프로토콜 포크도 없이
허용된 대상에 회차별 한도 이하 호출을 반복하면 된다. 게이트에는 실패 확률이 가장
낮은 것을 건다.

Agent Wallet의 지출 한도가 **일일 리셋**이라는 점이 이 클래스의 정조준 근거다.
회차별·일별 한도를 모두 지키면서 롤링 윈도우 누적으로 자산을 고갈시킬 수 있다.

## 합격 기준

### G1. 포크 환경이 결정론적이다
- anvil이 **고정 블록**에서 포크된다. 블록 번호가 `docs/baseline-config.md`에 기록된다.
- 같은 명령을 두 번 실행하면 최종 상태 해시가 같다.

### G2. baseline이 살아 있다 (네거티브 컨트롤)
- 한도를 초과하는 호출 **1건이 실제로 revert 된다.**
- 허용목록 밖 대상 호출 **1건이 실제로 revert 된다.**
- 두 revert의 사유가 로그에 enforcer 이름과 함께 남는다.

**G2 없이 G3을 주장하지 않는다.** baseline이 꺼져 있었을 가능성을 배제하는 유일한 증거다.

### G3. 위반 트레이스가 전 계층을 통과한다
- N회 호출 전부가 배포된 enforcer 집합을 통과한다 (revert 0건).
- 각 호출이 회차 한도와 일일 한도를 **모두 만족**한다.
- 시퀀스 종료 후 오라클 환산 포트폴리오 가치가 시작 대비 **유의미하게 감소**한다.
  - 감소폭 임계는 실행 후 실측으로 확정한다. 임계를 먼저 정하고 거기 맞추지 않는다.

### G4. 트레이스가 검증기 입력으로 쓸 수 있는 형태다
`traces/cumulative-loss.json` 에 최소한 다음이 들어간다.

| 필드 | 내용 |
| --- | --- |
| `fork` | 체인 ID, 블록 번호, delegation-framework 커밋 해시 |
| `baseline` | 배포된 enforcer 주소와 파라미터 |
| `steps[]` | 회차별 calldata, 대상, 값, 통과한 enforcer 목록, 가스 |
| `states[]` | 회차별 사전/사후 잔액 (자산별) |
| `oracle` | 사용한 피드 주소와 해당 블록의 가격 |
| `result` | 시작/종료 포트폴리오 가치, 감소액 |

스키마는 `verifier/`의 Pydantic 모델과 **같은 정의**를 쓴다. TS가 쓰고 Python이 읽는다.

## 산출물

- `traces/negative-control.json` — 차단되는 트레이스 (G2)

## 검증 시 확인할 것 (Opus)

1. G3의 "통과"가 실제 enforcer 평가 결과인가, 아니면 enforcer를 붙이지 않고 통과한
   것처럼 기록한 것인가
2. 한도 파라미터가 현실적인가 — 통과시키려고 한도를 비정상적으로 크게 잡지 않았는가
3. 포트폴리오 가치 감소가 오라클 환산 결과인가, 임의 계산인가
4. 재실행 시 같은 결과가 나오는가
