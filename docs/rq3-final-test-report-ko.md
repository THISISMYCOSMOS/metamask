# RQ3 최종 실험 보고서 — 승인된 사용자 의도에 대한 결과 상태 검증

작성일: 2026-09-08 (KST)

> 상태: 신규 비교 실험과 기존 증거 재검증 완료

## 1. 연구 목적과 실험 선정 이유

이 연구에서 LLM의 역할은 자연어 요청을 제한된 불변식 스키마의 정책으로 제안하는 것이다. 사용자가 그 정책을 검토하고 승인한 뒤, 결정론적 검증기가 거래 후보의 예상 결과와 승인된 불변식을 비교한다. 위반 후보는 전송 경계에 도달하기 전에 거절하고, 허용 후보는 실제 실행 결과를 확인한다. 따라서 RQ3의 보호 대상은 사용자의 숨은 의도를 추정한 값이 아니라 **사용자가 승인한 불변식으로 표현된 의도**다.

최종 실험은 다음 세 질문에 답하도록 구성한다. 제품 기능을 추가하는 것이 아니라, 각 주장을 실제 증거로 뒷받침하기 위한 테스트용 구현과 실행이다.

| 묶음 | 연구 질문 | 선택 이유 |
| --- | --- | --- |
| A. 기존 보호 대비 추가 효과 | 실제 기존 Caveat가 허용한 의도 위반 후보를 우리 게이트가 전송 전에 차단하고, 정상 후보는 실행시키는가? | 기존 G3의 실행 결과와 오프라인 판정 사이에 남아 있던 실행 전 차단 증거를 보강한다. |
| B. Sepolia 실제 지갑 사례 | 자연어 정책 제안과 승인, 게이트 판단, 실제 지갑 전송 및 무전송 거절이 연결되는가? | 실제 환경의 실행 가능성을 기존 허용·거절 한 쌍으로 확인한다. |
| C. 검증 위치 비교 | 현재 검증 위치는 언제 효과가 있고, 검증 이후 상태 변화가 생기면 어떤 한계가 나타나는가? | 현재 위치의 효과를 설명하면서 보호가 제한되는 조건도 실험 결과로 제시한다. |

A와 C는 승인된 정책을 고정한다. 비교마다 LLM을 재호출해 정책이 달라지면 게이트 유무나 위치의 효과를 분리하기 어렵다. 자연어 해석의 일반적 정확도는 RQ2의 범위이고, B에서는 저장된 자연어·제안·승인 증거가 실행 후보와 연결되는지를 다룬다.

## 2. 기존 G3 증거와 추가 실험의 관계

기존 G3는 고정 메인넷 포크에서 실제 EIP-712 서명과 여섯 Caveat가 포함된 `redeemDelegations`를 20회 실행한 하나의 시퀀스다. 거래별 500 USDC, 총 10,000 USDC가 전송됐고 최종 USDC 잔액은 0이다. 기간별 전송 횟수는 `3,4,4,4,4,1`이다. 이 결과는 설정된 Caveat 조건을 모두 만족하면서 별도의 포트폴리오 결과 정책을 위반하는 구성이 가능함을 보여준다.

| 기존 평가 | 불변식 또는 결과 | 증거 성격 |
| --- | --- | --- |
| G3 가치 하한 위반 | 관측 최소 18,981.1115161 USD < 승인 하한 26,979.2516761 USD | 실제 G3 트레이스를 정규화한 후보의 오프라인 평가 |
| G3 누적 손실 상한 위반 | 24시간 최대 2,499.4188 USD > 승인 상한 1,999.53504 USD | 같은 후보의 오프라인 평가 |
| 대응 정상 후보 허용 | 가치 27,479.1354361 USD, 누적 손실 1,499.65128 USD | 300 USDC × 5회로 구성한 반사실적 후보, 온체인 실행 아님 |

이 오프라인 거절만으로 G3 실행을 실제 전송 전에 차단했다고 쓸 수는 없다. 신규 A는 실제 기존 보호를 유지한 채 우리 게이트의 유무만 바꾸어 전송·거절과 사후 상태를 연결하기 위한 비교다. 새 실험에서 사용한 불변식과 G3 포트폴리오 불변식은 각각 명시하며, 새 결과를 G3 전체 시퀀스의 실시간 차단 증거로 바꾸어 해석하지 않는다.

## 3. 실험 A — 실제 기존 보호와 우리 게이트의 비교

### 3.1 가설과 비교 단위

가설은 “기존에 설정한 Caveat를 모두 만족하는 거래라도, 승인된 잔액 하한을 위반하면 추가된 게이트가 그 거래의 전송을 막을 수 있다”이다. 정상 후보와 위반 후보를 각각 기존 Caveat만 적용한 경로와 같은 Caveat에 우리 게이트를 추가한 경로에 넣는다. 비교 단위는 개별 후보의 두 경로이며 총 네 셀이다.

단일 자산 하한을 사용하는 이유는 기존 전송 경계의 `DelegatedFloorGate`가 실제 지원하는 결과 불변식이기 때문이다. 포트폴리오·누적 손실 평가기를 새로운 실시간 제품 기능으로 확장하지 않고, 이미 있는 검증의 집행 효과를 직접 확인한다. G3의 포트폴리오 평가 결과는 2절의 별도 증거로 남는다.

### 3.2 설계 조건과 방법의 타당성

독립 설계 검토는 다음 조건 아래 이 방식이 좁은 추가 보호 효과 질문에 적합하다고 판정했다.

| 변수 | 고정 또는 변경 방법 |
| --- | --- |
| 네트워크 | 외부 포크 없는 격리된 로컬 Anvil; 서명 helper와 실제 로컬 체인의 chain ID를 1로 일치시킴 |
| 기존 보호 | 핀 Delegation Framework의 실제 Manager, 스마트 계정 및 여섯 Caveat 구현 |
| 시작 자산 잔액 | 10,000 토큰 단위 |
| 결과 불변식 | `assetBalanceFloor`: 최소 9,700 토큰 단위 유지 |
| 기존 감소 상한 | `ERC20BalanceChangeEnforcer`의 `enforceDecrease=true`, 최대 감소 500 |
| 기존 기간 전송 상한 | 같은 기간 내 2,000 |
| 정상 후보 | 100 전송, 예상 잔액 9,900 |
| 의도 위반 후보 | 500 전송, 예상 잔액 9,500 |
| 유일한 경로 차이 | 기존 Caveat만 사용하는가, 동일 Caveat에 우리 게이트를 추가하는가 |
| 상태 격리 | 각 셀을 같은 배포 후 snapshot으로 복원 |

핀 소스의 감소 검사식은 `after >= before - amount`다. 따라서 두 후보 모두 기존 감소 상한 500을 만족한다. 하한 9,700은 사용자가 최종적으로 남기려는 잔액을 나타내므로, 500 전송은 기존 보호 범위 안에서도 이 별도 의도를 위반한다. 보호 설정을 경로마다 변경해 결과를 유도하지 않는다.

이 구성은 해당 Caveat로 절대 잔액 하한을 표현하는 것이 언제나 불가능하다는 증명은 아니다. 특정 상태에서 기존 상한을 더 좁히면 같은 거래를 막을 수도 있다. 실험의 질문은 **고정한 기존 보호 설정에 별도로 승인한 결과 조건을 추가했을 때 실제로 추가 차단이 일어나는가**이다.

정상 100과 위반 500은 결과 조건의 양쪽을 검사하기 위해 의도적으로 고른 통제 사례다. 무작위 수집한 거래 표본이 아니므로 정확도·공격 발생률·오탐률·미탐률을 추정하지 않는다. 정상 사례는 모든 후보를 무조건 거절하는 구현을 배제하고, 위반 사례는 기존 조건과 사용자 결과 조건이 서로 다른 역할을 수행하는 상황을 드러낸다. 501 대조군은 기존 상한을 넘는 요청이 실제로 거절되는지 확인한다.

토큰 decimals는 6이며, 10,000 토큰은 `10000000000`, 하한 9,700은 `9700000000`, 100 전송은 `100000000`, 500 전송은 `500000000` base units다. 보고서 표는 읽기 쉬운 토큰 수량을 사용하고 원본 JSON은 정수 base units를 보존한다.

신규 로컬 정책과 승인은 실험용 fixture로 표시한다. 이는 연구에서 선택한 승인 정책 경계를 재현하기 위한 입력이며, 새로운 LLM 호출이나 실제 사용자의 승인 행사를 기록한 것이 아니다. 자연어 정책 제안·승인·지갑 실행 연결은 B의 기존 증거로 설명한다.

### 3.3 실행 과정 및 관측 결과

테스트 구현은 다음 순서로 비교를 구성한다.

1. 프레임워크 핀 커밋과 소스 변경 유무를 확인하고, 별도 임시 디렉터리에 실제 컨트랙트를 빌드한다.
2. 새 로컬 노드에 Manager, 필요한 라이브러리, HybridDeleGator 구현과 프록시, 여섯 Enforcer 및 토큰을 배포한다. 배포 receipt와 실제 bytecode를 기록한다.
3. 고정 Caveat를 가진 root delegation을 EIP-712로 서명하고, 실험용 승인 정책과 해시를 만든다. 이 위임 서명은 셀 실행 전에 한 번 생성되며 이후 후보 전송의 서명과 구분한다.
4. 501 토큰 전송의 실제 `redeemDelegations`를 `eth_call`로 검사해 기존 감소 상한 500이 작동하는지 확인한다. 이 음성 대조군은 네 비교 셀의 일부가 아니라 기존 보호가 실제 활성화됐는지 확인하는 보조 검사다.
5. 정상·위반 후보별로 정확한 outer redemption을 snapshot 위에서 서명·실행하고, receipt·Transfer 이벤트·실측 잔액을 읽는다. 그런 다음 snapshot을 복원해 블록·상태 root·잔액·nonce·기간 사용량이 원래 상태와 일치하는지 확인한다.
6. 관측한 사후 잔액으로 후보를 구성한다. 같은 후보를 기존 Caveat 경로와 추가 게이트 경로에 각각 적용한다. 각 경로 시작 전 동일 snapshot을 복원한다.
7. 전송 경로에서는 성공 receipt, 정확한 거래 필드, Transfer와 기간 전송 이벤트, 실제 Enforcer 호출 trace 및 사후 잔액을 확인한다. 거절 경로에서는 후보 서명·전송 호출 0회와 상태 불변을 확인한다.
8. 후보·정책·승인·보호 설정·실행 요청의 해시와 시작 상태가 비교 쌍 사이에서 일치하는지 단언한다.

시뮬레이션은 실제 로컬 거래를 실행한 뒤 되돌리는 방식이다. 그러므로 “무전송 거절”은 **상태 복원 이후 실제 전송 단계에서 후보를 보내지 않았다**는 뜻이다. 실험 전체에서 RPC 전송이 한 번도 없었다는 뜻으로 사용하지 않는다. 또한 코드의 `gateInvocations`는 게이트 진입 횟수이며, 기록용 평가와 게이트 내부 평가를 합친 evaluator 호출 횟수가 아니다.

### 3.4 실행 결과

최종 실행은 2026-09-08 12:46:43 KST에 시작해 12:50:25 KST에 끝났고, 하네스의 전체 단언이 통과했다. 두 시나리오의 시뮬레이션과 네 비교 셀은 각각 같은 배포 후 상태로 복원되었다.

| 시나리오 | 경로 | 판정·실행 | 후보 서명/전송 | 최종 delegator 잔액 | 하한 위반 |
| --- | --- | --- | ---: | ---: | --- |
| 정상 100 | 기존 여섯 Caveat만 | 실제 `redeemDelegations` 성공 | 1 / 1 | 9,900 | 아니오 |
| 정상 100 | 같은 Caveat + 결과 게이트 | 게이트 허용 후 실제 실행 성공 | 1 / 1 | 9,900 | 아니오 |
| 위반 500 | 기존 여섯 Caveat만 | 실제 `redeemDelegations` 성공 | 1 / 1 | 9,500 | 예 |
| 위반 500 | 같은 Caveat + 결과 게이트 | `ASSET_BALANCE_FLOOR_VIOLATION` 거절 | 0 / 0 | 10,000 | 아니오 |

정상 후보의 실제 거래 해시는 두 경로 모두 `0x5ed48f063d4e49475e9f5be7abc0ca43a102bfc2baf0b2354ef4975a789676a3`이다. 위반 후보는 기존 Caveat 경로에서 `0x94108e962f80af2b1c031a9baa1766deef1781590aa33061eaa8ae94d76e9b24`로 실행됐다. 동일 snapshot과 동일 서명 입력을 사용했기 때문에 동일 동작의 거래 해시도 일치한다.

각 성공 셀에서 receipt, outer transaction 필드, delegator→recipient `Transfer`, `TransferredInPeriod`, 사후 잔액과 delegate nonce를 확인했다. `debug_traceTransaction`에서는 여섯 Enforcer 주소가 각각 네 번 관측되어 실제 before/after hook 경로를 통과했음을 확인했다. 위반 게이트 셀에는 signed raw transaction과 receipt가 없고 후보 signer·sender 호출이 모두 0이며, 시작 상태와 종료 상태가 같다.

정상과 위반 후보의 paired route는 각각 candidate, execution, policy, approval, signed protection hash와 전체 초기 상태가 일치했다. 정상 candidate hash는 `0x2902c9ec6ae8837095ef05fda18ce1af410884f20fa7f0b1b6245b2688d40073`, 위반 candidate hash는 `0xc4cda766c006f57dfce15dbc739a2976d9a3609eda8b62a6c502e46f19151a5e`다. 공통 delegation hash는 `0x42026c4f912ac550da0d13d3bbc3229c8f400e3931893706f6ca7caa4951a8dd`다.

기존 보호 음성 대조군에서는 501 토큰의 exact signed redemption `eth_call`이 `ERC20BalanceChangeEnforcer:exceeded-balance-decrease`로 거절됐고 상태가 유지됐다. 따라서 위반 500의 baseline 성공은 Caveat를 비활성화한 결과가 아니라, 설정된 최대 감소 경계 안에 있는 거래의 실제 허용 결과다.

### 3.5 이 결과가 답하는 질문

같은 기존 보호 설정 아래, 정상 후보는 추가 게이트가 있어도 실행됐다. 반면 기존 여섯 Caveat가 허용해 잔액을 9,500으로 만든 후보는 승인 하한 9,700을 적용한 게이트에서 outer transaction 서명 전에 차단됐다. 그러므로 **고정한 기존 보호 구성에 승인된 결과 불변식을 추가했을 때, 기존 보호가 허용한 의도 위반 후보를 추가로 차단했다**는 가설은 이 통제 사례에서 지지된다.

이 결과는 단일 전송의 `assetBalanceFloor`에 대한 로컬 비교다. G3의 20단계 누적 손실 정책을 실시간으로 차단했다거나, 기존 보호의 모든 가능한 설정보다 우월하거나, 원격 Agent Wallet의 네이티브 집행을 증명하지 않는다.

## 4. 실험 B — 기존 Sepolia 사례의 재사용

### 4.1 진행 이유와 과정

| 확인 기준 | 필요한 증거 | 기준이 빠졌을 때 생기는 문제 |
| --- | --- | --- |
| 실제 기존 보호 | 핀 소스의 실제 DelegationManager·Caveat 배포와 서명된 redemption | 보호를 흉내 낸 대조군의 결과를 기존 보호 대비 효과로 오해할 수 있다. |
| 동일 조건 비교 | 동일 초기 snapshot, 정책, Caveat terms, 서명 위임, 경로별 동일 후보 | 서로 다른 설정에서 나온 차이를 우리 게이트의 효과로 잘못 돌릴 수 있다. |

### 6.2 실행 중 확인한 오류와 처리

첫 신규 실험은 HybridDeleGator 배포 bytecode의 Solidity library placeholder가 연결되지 않아 배포 단계에서 실패했다. `bytecode.linkReferences`에 지정된 실제 `SCL_RIP7212` 라이브러리를 로컬에 배포하고 정확한 offset·length에 주소를 연결하도록 테스트 하네스를 보완했다. 연결된 bytecode와 배포 주소·runtime hash도 증거에 포함한다. 프레임워크 소스 자체를 수정한 것은 아니다.

그다음 실행에서는 라이브러리 배포, 감소 상한 음성 대조군, 정상 후보의 snapshot 시뮬레이션을 통과했지만, ABI 디코딩 주소의 checksum 대소문자 표기와 원본 주소 문자열을 직접 비교하던 테스트 단언이 실패했다. 비교 기준을 permission context의 ABI 디코딩→재인코딩 바이트 일치로 수정했다. 이 실패는 불변식 차단 결과가 아니라 테스트 코드의 표현 비교 오류였으며, 수정 이후 전체 비교 실행이 통과했다.

최종 성공 결과는 위 실패 실행과 구분한다. 실패 실행을 통과 결과로 합산하지 않았으며, 실행 준비와 표현 비교 단계의 실패를 연구 가설의 반증으로 해석하지 않는다.

## 7. 연구 본문과 부록의 구성

본문에는 A의 동일 조건 비교표, B의 실제 허용·거절 한 쌍, C의 위치 비교표와 한계를 남긴다. G3는 A를 설명하는 기존 배경 증거로 요약한다. 20회 거래 로그를 독립 표본 20개로 세지 않는다.

부록에는 Caveat 정상 작동 대조군, 서명·calldata·이벤트 결합 검증, 변조·컨텍스트 변경·RPC 실패 단위 검사, 명령·버전·원본 JSON·해시를 배치한다. 단위 테스트 개수는 구현 검증 수치이며 연구 효과의 표본 수가 아니다.

## 8. 최종 해석

세 실험 묶음은 서로 다른 질문을 담당한다.

1. 신규 A는 실제 여섯 Caveat를 유지한 동일 조건 비교에서 결과 게이트의 추가 효과를 확인했다. 정상 후보는 두 경로에서 모두 실행됐고, 기존 Caveat가 허용한 하한 위반 후보는 결과 게이트가 outer transaction 서명 전에 차단했다.
2. 기존 B는 저장된 자연어 요청, Gemini 제안으로 기록된 정책, 정확한 proposal hash 승인, Sepolia direct 정상 실행과 같은 정책의 무전송 거절을 연결한다. 이 증거는 실제 Agent Wallet 경로의 제한된 실행 가능성을 뒷받침한다.
3. 기존 C는 현재 `pre-submit` 위치가 안정된 상태의 최초 위반을 막지만 검증 이후 잔액 변경은 놓칠 수 있고, 더 늦은 통제 `pre-sign` 검사는 그 사례에서 stale context를 거절했음을 보여준다.

따라서 RQ3에서는 다음과 같이 결론 낼 수 있다.

> 제한된 통제 실험에서 승인된 결과 상태 불변식을 기존 Delegation Framework 보호에 추가하자, 기존 여섯 Caveat가 허용한 잔액 하한 위반 후보가 outer transaction 서명 전에 거절됐고 정상 후보는 실제 실행됐다. 별도의 Sepolia direct 사례에서는 기록된 자연어 정책 제안·승인과 허용·거절 경로가 실제 Agent Wallet 실행 증거에 연결됐다. 현재 애플리케이션 게이트는 상태가 유지되는 조건에서 사용자 승인 의도를 추가로 보호하지만, 검증 이후의 상태 변화까지 원자적으로 보장하지 않는다.

연구 본문에서는 `기존 보호보다 일반적으로 더 안전하다`보다 **`고정한 기존 보호 구성에서 승인된 결과 불변식에 대한 추가 차단 효과를 관측했다`**고 표현한다. 이는 이번 비교가 실제로 측정한 범위와 일치한다.
